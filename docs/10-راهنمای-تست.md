# 1- مقدمه

این سند روش اجرای تست‌ها، ساختار test suite، استاندارد نوشتن تست جدید و نکات کنترل کیفیت پروژه Crumbs را توضیح می‌دهد. هدف آن این است که توسعه‌دهنده یا تیم QA بتواند با کمترین ابهام تست‌های موجود را اجرا کند، جای درست تست جدید را تشخیص دهد و از تغییر رفتارهای حساس مانند checkout، payment، inventory و UI جلوگیری کند.

Crumbs از pytest و pytest-django برای تست استفاده می‌کند. مسیر استاندارد تست پروژه، اجرای pytest روی پوشه `tests` است. Django check نیز برای بررسی سلامت configuration و registry پروژه استفاده می‌شود.

## 1-1- هدف تست در پروژه

| هدف | توضیح |
| --- | --- |
| محافظت از flowهای کسب‌وکار | checkout، payment، inventory و order lifecycle باید پس از تغییرات پایدار بمانند. |
| جلوگیری از regression | تغییر UI، admin، terminology و payment callback نباید رفتارهای قبلی را بشکند. |
| پوشش edge caseها | خطاهای provider، webhook تکراری، race condition و داده نامعتبر باید کنترل شوند. |
| اطمینان از آماده‌سازی تولید | production settings، health endpointها، migration history و observability تست می‌شوند. |
| سرعت feedback | اجرای پیش‌فرض با SQLite in-memory سریع است و نیاز به Docker ندارد. |

## 1-2- فلسفه تست

| اصل | معنی عملی |
| --- | --- |
| تست رفتار، نه پیاده‌سازی داخلی | assertion باید روی خروجی، وضعیت مدل‌ها و contractهای کاربرمحور باشد. |
| mock کردن سرویس خارجی | تست پیش‌فرض نباید SMS یا payment API واقعی را صدا بزند. |
| جدا کردن تست سریع و سنگین | concurrency و load به محیط PostgreSQL یا staging نیاز دارند. |
| تست transactionهای حساس | موجودی و پرداخت باید در شرایط خطا و همزمانی بررسی شوند. |
| استفاده از fixture و factory | داده تست باید قابل بازتولید و خوانا باشد. |

# 2- ساختار تست‌ها

پوشه اصلی تست‌ها `tests` است. تنظیمات pytest در `pytest.ini` قرار دارد و test settings پروژه از `config/settings/test.py` استفاده می‌کند.

## 2-1- ساختار پوشه‌ها

```text
tests/
├── conftest.py
├── factories.py
├── payment_test_settings.py
├── mocks/
├── unit/
├── integration/
├── concurrency/
├── celery/
├── edge_cases/
└── load/
    └── README.md
```

## 2-2- مسئولیت هر بخش

| مسیر | مسئولیت |
| --- | --- |
| `tests/conftest.py` | fixtureهای مشترک، تنظیمات autouse و mockهای عمومی |
| `tests/factories.py` | ساخت داده تست مانند user، product، order، cart و coupon |
| `tests/payment_test_settings.py` | تنظیمات تستی پرداخت برای Stripe و Zarinpal |
| `tests/mocks` | providerهای mock برای payment و SMS |
| `tests/unit` | تست serviceها، viewهای کوچک، admin، UI، health، settings و migration |
| `tests/integration` | flowهای چندمرحله‌ای checkout، payment، coupon، referral، SMS و COD |
| `tests/concurrency` | تست همزمانی stock و checkout با PostgreSQL |
| `tests/celery` | تست task reliability، idempotency و رفتار Celery در حالت eager |
| `tests/edge_cases` | سناریوهای failure، abuse، webhook تکراری و خطاهای غیرعادی |
| `tests/load` | راهنمای load simulation؛ کد load test دائمی در repository وجود ندارد. |

## 2-3- تنظیمات pytest

| تنظیم | مقدار |
| --- | --- |
| settings | `config.settings.test` |

| الگوی class | `Test*` |
| الگوی function | `test_*` |

## 2-4- Markerهای ثبت‌شده

# 5- بررسی سلامت پروژه

`python manage.py check` برای بررسی configuration، app registry و خطاهای سطح Django استفاده می‌شود. این دستور جایگزین تست نیست، اما قبل از اجرای تست یا deploy کمک می‌کند خطاهای پایه زودتر دیده شوند.

## 5-1- اجرای check

```bash
python manage.py check
```

برای اجرای صریح با test settings:

```bash
python manage.py check --settings=config.settings.test
```

## 5-2- تفسیر نتیجه

| نتیجه | معنی |
| --- | --- |
| بدون خطا | configuration فعلی از نظر Django check مشکلی نشان نداده است. |
| warning | نیاز به بررسی دارد، اما لزوماً اجرای پروژه را متوقف نمی‌کند. |
| error | باید قبل از ادامه توسعه، تست یا deploy رفع شود. |

# 6- ساختار نوشتن تست جدید

تست جدید باید در نزدیک‌ترین پوشه به نوع ریسک قرار گیرد. اگر تغییر فقط یک service کوچک را تغییر می‌دهد، معمولاً `tests/unit` کافی است. اگر چند app با هم درگیر هستند، تست integration مناسب‌تر است.

## 6-1- قوانین نام‌گذاری

| مورد | الگو |
| --- | --- |
| فایل تست | `test_feature_name.py` |
| class تست | `TestFeatureName` |
| function تست | `test_expected_behavior` |
| marker | فقط markerهای ثبت‌شده در `pytest.ini` |

## 6-2- انتخاب محل تست

| نوع تغییر | محل پیشنهادی |
| --- | --- |
| service کوچک | `tests/unit` |
| view یا template عمومی | `tests/unit` |
| checkout چندمرحله‌ای | `tests/integration` |
| payment callback | `tests/unit` یا `tests/integration` بر اساس scope |
| race condition | `tests/concurrency` |
| task پس‌زمینه | `tests/celery` |
| failure یا abuse scenario | `tests/edge_cases` |

## 6-3- الگوی Arrange / Act / Assert

```python
def test_checkout_creates_order(client, user, product):
    # Arrange
    cart = create_cart_with_item(user, product)
    client.force_login(user)

    # Act
    response = client.post("/checkout/", data={...})

    # Assert
    assert response.status_code == 302
    assert cart.items.count() == 0
```

این الگو باعث می‌شود هدف تست روشن بماند و خواننده بداند داده اولیه، عمل مورد بررسی و انتظار نهایی چیست.

Checkout از حساس‌ترین flowهای پروژه است، چون cart، order، payment، inventory و UI را همزمان درگیر می‌کند.

## 7-1- فایل‌های مرتبط

| فایل | پوشش |
| --- | --- |
| `tests/integration/test_flow_cafe_checkout.py` | checkout کافه، پرداخت حضوری، پرداخت آنلاین، سفارش مهمان و نمایش پیام |
| `tests/integration/test_flow_online_payment.py` | checkout آنلاین، خطای provider، retry و callback |
| `tests/unit/test_cart_checkout_ux.py` | متن‌ها و UX سبد و checkout |
| `tests/unit/test_cart_quantity_update.py` | تغییر تعداد در سبد |

## 7-2- سناریوهای موجود

| سناریو | رفتار مورد انتظار |
| --- | --- |
| پرداخت حضوری | سفارش با status `awaiting_payment` و payment provider `cash` ساخته می‌شود. |
| پرداخت آنلاین | سفارش با status `pending_payment` وارد gateway flow می‌شود. |

| سفارش کاربر واردشده | به صفحه جزئیات سفارش در account هدایت می‌شود. |
| counter card عمومی | گزینه عمومی checkout نیست و سفارش ساخته نمی‌شود. |
| خطای provider | سفارش ناقص ساخته نمی‌شود و cart قابل retry باقی می‌ماند. |

## 8-2- Online Payment

| مورد | تست می‌شود |
| --- | --- |

## 8-3- Cash و Counter

| مورد | تست می‌شود |
| --- | --- |
| `cash` در checkout عمومی | سفارش در انتظار پرداخت حضوری ایجاد می‌شود. |
| `counter_card` | در checkout عمومی انتخاب قابل قبول نیست. |
| دریافت وجه در admin/service | payment به `succeeded` و order به وضعیت مناسب منتقل می‌شود. |
| idempotency دریافت وجه | اجرای دوباره action نباید stock را دوباره مصرف کند. |

## 8-4- Failure و Success

| حالت | انتظار |
| --- | --- |
| provider error | خطا به checkout منتقل می‌شود و 500 خام تولید نمی‌شود. |
| callback موفق | payment موفق و order paid/confirmed می‌شود. |
| callback تکراری | event دوباره پردازش اثر تکراری ایجاد نمی‌کند. |
| stale payment | payment ناموفق و order لغو می‌شود، reservation آزاد می‌شود. |

# 14- پرسش‌های متداول

## 14-1- دستور اصلی اجرای تست چیست؟

دستور اصلی پروژه `pytest -q` است.

## 14-2- آیا اجرای پیش‌فرض به Docker نیاز دارد؟

خیر. اجرای پیش‌فرض با SQLite in-memory انجام می‌شود و Docker لازم ندارد.

## 14-3- چه زمانی PostgreSQL لازم است؟

برای تست‌های marker `concurrency` که به locking واقعی `select_for_update` نیاز دارند.

## 14-4- آیا تست‌ها payment API واقعی را صدا می‌زنند؟

در suite پیش‌فرض خیر. payment و webhookها با mock یا provider تستی اجرا می‌شوند.

## 14-5- تست‌های Zarinpal چه زمانی اجرا می‌شوند؟

تست‌های marker `zarinpal_integration` فقط وقتی اجرا می‌شوند که `ZARINPAL_MERCHANT_ID` در محیط تنظیم شده باشد.

## 14-6- آیا coverage percentage رسمی وجود دارد؟

در این repository ابزار pytest-cov موجود است، اما این سند درصد coverage رسمی اعلام نمی‌کند.

## 14-7- آیا CI pipeline در repository وجود دارد؟

این سند CI pipeline موجود مستند نمی‌کند. تست‌ها محلی و بر اساس دستورهای pytest و راهنمای موجود اجرا می‌شوند.

## 14-8- Load test کجا قرار دارد؟

کد load test دائمی در repository وجود ندارد. راهنمای آن در `tests/load/README.md` قرار دارد.

## 14-9- برای تغییر checkout کدام تست‌ها مهم‌ترند؟

`tests/integration/test_flow_cafe_checkout.py`، `tests/integration/test_flow_online_payment.py`، `tests/unit/test_cart_checkout_ux.py` و تست‌های reservation مرتبط.

## 14-10- برای تغییر admin کدام تست‌ها باید اجرا شوند؟

`tests/unit/test_admin_persian.py`، `tests/unit/test_admin_operations_dashboard.py`، `tests/unit/test_admin_ops_dashboard.py`، `tests/unit/test_kitchen_queue.py`، `tests/unit/test_pickup_screen.py` و `tests/unit/test_order_admin_actions.py`.

# 15- جمع‌بندی

تست‌های Crumbs برای محافظت از رفتارهای اصلی یک سامانه سفارش‌گیری کافه و بیکری طراحی شده‌اند. اجرای سریع پیش‌فرض با pytest، تست‌های integration برای flowهای اصلی، تست‌های concurrency روی PostgreSQL و تست‌های UI/Regression باعث می‌شوند تغییرات با ریسک کنترل‌شده انجام شوند.

در توسعه روزمره، اجرای `pytest -q` و `python manage.py check` حداقل کنترل پایه است. برای تغییرات حساس در checkout، payment و inventory باید تست‌های هدفمند همان حوزه نیز اجرا شوند.
