# 1- مقدمه

# 2- معماری محیط تولید

محیط تولید Crumbs با Docker Compose اجرا می‌شود. سرویس وب Django پشت Gunicorn قرار دارد و Nginx نقش Reverse Proxy، سرو فایل‌های Static و Media و مدیریت ترافیک HTTP/HTTPS را بر عهده می‌گیرد. PostgreSQL داده‌های اصلی را نگهداری می‌کند و Redis برای Cache، Session Cache، Broker و Result Backend مربوط به Celery استفاده می‌شود.

```text
Browser
  |
  | HTTP / HTTPS
  v
Nginx
  |----------------------.
  |                      |
  | static / media       |
  v                      |
Gunicorn                 |
  |                      |
  v                      |
Django                   |
  |----------------------|--------------------.
  |                      |                    |
  v                      v                    v
PostgreSQL             Redis            Celery Worker
                                               ^
                                               |
                                          Celery Beat
```

| لایه | پیاده‌سازی | مسئولیت |
| --- | --- | --- |
| Browser | مرورگر کاربر | ارسال درخواست، دریافت صفحات، ثبت فرم‌ها و مشاهده پاسخ |
| Nginx | سرویس `nginx` در `docker-compose.production.yml` | Reverse Proxy، TLS، سرو Static و Media |
| Gunicorn | تنظیمات `docker/gunicorn.conf.py` | اجرای فرآیند WSGI برای Django |
| Django | سرویس `web` | منطق برنامه، URLها، Viewها، Admin، سرویس‌ها و Templateها |
| PostgreSQL | سرویس `db` | پایگاه‌داده اصلی سفارش، پرداخت، موجودی، کاربر و گزارش‌ها |
| Redis | سرویس `redis` | Cache، Session Cache، Broker و Result Backend |
| Celery Worker | سرویس `celery_worker` | اجرای وظایف پس‌زمینه |
| Celery Beat | سرویس `celery_beat` | زمان‌بندی وظایف دوره‌ای |
| Static files | Volume به نام `static_volume` | خروجی Collectstatic و فایل‌های عمومی |
| Media files | Volume به نام `media_volume` | تصاویر محصول، فایل‌های آپلودی و رزومه‌ها |

## 2-1- سرویس‌های Docker Compose

| سرویس | نقش |
| --- | --- |
| `db` | اجرای PostgreSQL با تصویر `postgres:16-alpine` |
| `redis` | اجرای Redis با تصویر `redis:7-alpine` |
| `web` | اجرای Django و Gunicorn |
| `celery_worker` | اجرای Celery Worker برای صف‌های `default,sms,orders,analytics` |
| `celery_beat` | اجرای Celery Beat |
| `nginx` | Reverse Proxy و سرو Static/Media |
| `certbot` | دریافت و تمدید گواهی SSL از طریق Certbot |

# 3- پیش‌نیازها

پیش از استقرار باید سرور، دامنه، دسترسی‌ها و متغیرهای محیطی آماده باشند. نبود هر یک از این موارد می‌تواند باعث شکست Build، اجرا نشدن سرویس‌ها یا آماده نبودن سایت برای ترافیک واقعی شود.

| پیش‌نیاز | مقدار یا توضیح |
| --- | --- |
| سیستم‌عامل | Ubuntu 22.04 LTS یا نسخه جدیدتر |
| Docker | نسخه 24 یا جدیدتر |
| Docker Compose | پلاگین v2 |
| منابع سرور | حداقل پیشنهادی: 2 vCPU و 4 GB RAM برای Web، Celery، PostgreSQL و Redis |
| دامنه | دامنه واقعی برای محیط تولید |
| DNS | رکورد A برای دامنه اصلی و `www` به IP سرور |
| Firewall | باز بودن پورت‌های `80` و `443` و محدودسازی SSH |
| SSL | آماده‌سازی Certbot و مقدار `CERTBOT_EMAIL` |
| Production secrets | مقدارهای واقعی برای `.env` |
| پرداخت | مقدار معتبر `ZARINPAL_MERCHANT_ID` برای پرداخت زنده |
| پیامک | مقدار `KAVENEGAR_API_KEY` در صورت فعال بودن پیامک واقعی |

# 5- آماده‌سازی محیط

فایل `.env` نقطه اصلی تنظیم محیط تولید است. این فایل باید روی سرور ساخته شود، سطح دسترسی محدود داشته باشد و هرگز وارد Git نشود. بسیاری از کنترل‌های امنیتی production در `config/settings/prod.py` به مقدارهای همین فایل وابسته‌اند.

```bash
cp .env.example .env
chmod 600 .env
nano .env
```

| گروه | نمونه متغیرها |
| --- | --- |
| Django | `SECRET_KEY`، `DEBUG`، `ALLOWED_HOSTS`، `CSRF_TRUSTED_ORIGINS`، `SITE_URL` |
| Database | `POSTGRES_DB`، `POSTGRES_USER`، `POSTGRES_PASSWORD`، `POSTGRES_HOST` |
| Redis و Celery | `REDIS_URL`، `CELERY_BROKER_URL`، `CELERY_RESULT_BACKEND` |
| Payment | `DEFAULT_PAYMENT_PROVIDER`، `ZARINPAL_MERCHANT_ID`، `ZARINPAL_CALLBACK_URL` |
| SMS | `SMS_PROVIDER`، `SMS_ENABLED`، `KAVENEGAR_API_KEY` |
| HTTPS | `ENABLE_HTTPS`، `CERTBOT_EMAIL`، `SECURE_HSTS_SECONDS` |
| Monitoring | `SENTRY_DSN`، `SENTRY_ENVIRONMENT`، `SENTRY_RELEASE` |

## 5-1- اصول نگهداری Secretها

- فایل `.env` نباید در Git commit شود.
- مقدار `DEBUG` در محیط تولید باید `False` باشد.
- مقدار `SECRET_KEY` باید طولانی، یکتا و مخصوص همان محیط باشد.
- مقدارهای پرداخت و پیامک باید فقط روی سرور یا سامانه امن مدیریت secret نگهداری شوند.
- برای تغییرهای حساس، نسخه قبلی `.env` باید خارج از Git و در محل امن قابل بازیابی باشد.

# 6- Build و راه‌اندازی

راه‌اندازی اولیه با اسکریپت `deploy/deploy.sh` انجام می‌شود. این اسکریپت قبل از اجرا وجود `.env`، مقدار `SECRET_KEY`، مقدار `POSTGRES_PASSWORD` و غیرفعال بودن `DEBUG` را بررسی می‌کند.

## 6-1- بررسی Compose

پیش از اجرای واقعی، فایل Compose و مقداردهی متغیرها باید بررسی شود.

```bash
docker compose --env-file .env -f docker-compose.production.yml config > /dev/null
```

## 6-2- راه‌اندازی اولیه

```bash
chmod +x deploy/*.sh
./deploy/deploy.sh init
```

در اجرای اولیه، اسکریپت موارد زیر را انجام می‌دهد:

| مرحله | دلیل |
| --- | --- |
| Build سرویس‌های `web`، `celery_worker` و `celery_beat` | ساخت Imageهای برنامه |
| راه‌اندازی `db` و `redis` | آماده شدن وابستگی‌های اصلی |
| اجرای Migration | آماده‌سازی ساختار پایگاه‌داده |
| اجرای Collectstatic | آماده‌سازی فایل‌های Static برای Nginx |
| راه‌اندازی همه سرویس‌ها | فعال شدن Web، Nginx و پردازش پس‌زمینه |
| اجرای Health Check | بررسی اولیه پس از بالا آمدن سرویس‌ها |

## 6-3- اجرای Migration و Collectstatic

در صورت نیاز به اجرای جداگانه:

```bash
./deploy/deploy.sh migrate
./deploy/deploy.sh collectstatic
```

## 6-4- ساخت Superuser

پس از بالا آمدن سرویس Web، حساب مدیر اصلی از داخل Container ساخته می‌شود.

```bash
docker compose --env-file .env -f docker-compose.production.yml exec web python manage.py createsuperuser
```

Superuser باید فقط برای مالک فنی یا مدیر بسیار محدود استفاده شود. برای کار روزانه، حساب‌های `staff` با دسترسی محدود مناسب‌تر هستند.

# 7- تنظیم Reverse Proxy

Nginx ورودی اصلی ترافیک HTTP/HTTPS است. درخواست‌های پویا به سرویس Web منتقل می‌شوند و فایل‌های Static و Media مستقیم توسط Nginx سرو می‌شوند. این جداسازی باعث کاهش بار روی Django و ساده‌تر شدن مدیریت TLS می‌شود.

| مسئولیت | توضیح |
| --- | --- |
| Proxy به Gunicorn | انتقال درخواست‌های پویا به سرویس `web:8000` |
| Static | سرو فایل‌های Volume `static_volume` از مسیر Nginx |
| Media | سرو فایل‌های Volume `media_volume` |
| TLS | استفاده از گواهی‌های Certbot |
| محدودسازی رفتار فایل‌ها | جلوگیری از اجرای فایل‌های آپلودی به عنوان کد |

فایل‌های Nginx در مسیر `docker/nginx/` قرار دارند. اگر مقدار `DOMAIN` در `.env` تنظیم شده باشد، اسکریپت `deploy/render-nginx.sh` تنظیمات دامنه را render می‌کند.

# 8- راه‌اندازی HTTPS

راه‌اندازی HTTPS پس از موفق بودن استقرار اولیه HTTP انجام می‌شود. دلیل این ترتیب آن است که Certbot برای دریافت گواهی به دسترسی دامنه، DNS صحیح و پاسخ‌گویی Nginx روی پورت `80` نیاز دارد.

```bash
./deploy/init-ssl.sh
```

پس از دریافت گواهی، مقدارهای مرتبط با HTTPS در `.env` باید بازبینی شوند و سرویس‌ها به‌روزرسانی شوند.

```bash
./deploy/deploy.sh update
```

| مورد | نکته |
| --- | --- |
| `ENABLE_HTTPS` | پس از فعال شدن SSL باید `True` باشد |
| `SITE_URL` | باید با `https://` تنظیم شود |
| `CSRF_TRUSTED_ORIGINS` | باید دامنه‌های HTTPS را شامل شود |
| `SECURE_HSTS_SECONDS` | فقط پس از اطمینان از کارکرد HTTPS فعال شود |
| `CERTBOT_EMAIL` | برای صدور و تمدید گواهی لازم است |

# 9- بررسی سلامت سرویس

Crumbs دو Endpoint اصلی برای بررسی وضعیت دارد. Health Endpoint برای زنده بودن فرآیند استفاده می‌شود و Readiness Endpoint برای آماده بودن وابستگی‌های اصلی مانند Database، Redis، Celery Broker و Migrationها.

| Endpoint | نقش | وابستگی به Database |
| --- | --- | --- |
| `/health/` | بررسی liveness | ندارد |
| `/ready/` | بررسی readiness | دارد |
| `/health/full/` | diagnostics کامل‌تر | در production پیش‌فرض فعال نیست مگر با `HEALTH_FULL_ENABLED` |

## 9-1- دستورهای بررسی

```bash
curl -sS "${SITE_URL}/health/"
curl -sS "${SITE_URL}/ready/"
./deploy/healthcheck.sh
```

## 9-2- پاسخ مورد انتظار

| مسیر | انتظار |
| --- | --- |
| `/health/` | پاسخ موفق با وضعیت سرویس |
| `/ready/` | پاسخ موفق با `ready: true` در حالت سالم |
| `/ready/` در حالت خطا | HTTP 503 و مشخص شدن check ناموفق |

اسکریپت `deploy/healthcheck.sh` علاوه بر `/health/`، دسترسی به `static/css/crumbs.css`، `robots.txt` و `sitemap.xml` را هم بررسی می‌کند.

# 10- بررسی پس از استقرار

پس از بالا آمدن سرویس‌ها، فقط زنده بودن Containerها کافی نیست. باید مسیرهای اصلی کاربر و مدیر بررسی شوند تا مشکل در Static، Media، Admin، Checkout یا پرداخت پیش از Go Live مشخص شود.

| بخش | بررسی پیشنهادی |
| --- | --- |
| صفحه اصلی | باز شدن سایت از دامنه واقعی |
| Static files | بارگذاری CSS و JavaScript |
| Media files | نمایش تصاویر محصول یا فایل‌های آپلودی موجود |
| Admin | ورود به `/admin/` با Superuser |
| سفارش | مشاهده محصول، افزودن به سبد و شروع Checkout |
| Checkout | ثبت سفارش با داده معتبر |
| پرداخت | بررسی مسیر Zarinpal یا حالت Sandbox در صورت فعال بودن |
| پیامک | بررسی Provider و لاگ ارسال در صورت فعال بودن SMS |
| Health | موفق بودن `/health/` |
| Readiness | موفق بودن `/ready/` |

برای ماتریس کامل تست دستی باید از `docs/LAUNCH_TEST_PLAN.md` استفاده شود.

# 11- Backup و Restore

Backup و Restore در Crumbs با اسکریپت‌های اختصاصی انجام می‌شود. این سند فقط نمای کلی را توضیح می‌دهد؛ روش کامل، هشدارها و سناریوهای Restore در `docs/BACKUP_RESTORE.md` مستند شده است.

| عملیات | دستور اصلی |
| --- | --- |
| Backup پایگاه‌داده | `./deploy/backup.sh db` |
| Backup فایل‌های Media | `./deploy/backup.sh media` |
| Backup کامل | `./deploy/backup.sh all` |
| Restore پایگاه‌داده | `CONFIRM_RESTORE=yes ./deploy/restore.sh db BACKUP_FILE` |
| Restore فایل‌های Media | `CONFIRM_RESTORE=yes ./deploy/restore.sh media BACKUP_FILE` |

Restore عملیات destructive است. در فروشگاه زنده، بازگرداندن پایگاه‌داده قدیمی می‌تواند باعث از دست رفتن سفارش‌ها، پرداخت‌ها یا تغییرهای جدید شود. تصمیم Restore باید فقط با تأیید مالک فنی و پس از بررسی اثر عملیاتی انجام شود.

# 12- مانیتورینگ

مانیتورینگ Crumbs بر پایه لاگ‌های ساختاریافته، Health Endpoint، Readiness Endpoint و Sentry اختیاری طراحی شده است. جزئیات کامل در `docs/OBSERVABILITY.md` قرار دارد.

| ابزار | کاربرد |
| --- | --- |
| Docker logs | مشاهده لاگ سرویس‌های Web، Nginx و Celery |
| فایل‌های log | نگهداری لاگ‌های Django، Celery و Requestها |
| Sentry | ثبت خطاهای برنامه و خطاهای Celery در صورت تنظیم `SENTRY_DSN` |
| `/health/` | بررسی زنده بودن سرویس Web |
| `/ready/` | بررسی آمادگی Database، Redis، Broker و Migrationها |

## 12-1- مشاهده لاگ‌ها

```bash
docker compose -f docker-compose.production.yml logs -f web
docker compose -f docker-compose.production.yml logs -f celery_worker
docker compose -f docker-compose.production.yml logs -f celery_beat
```

در لاگ‌های عملیاتی نباید secret، رمز، token یا اطلاعات حساس پرداخت ثبت شود. سند Observability توضیح می‌دهد چه داده‌هایی در Sentry ارسال نمی‌شوند.

# 13- انتشار نسخه جدید

انتشار نسخه جدید باید با Backup، به‌روزرسانی کد، اجرای Migration، Collectstatic، Restart سرویس‌ها و بررسی سلامت همراه باشد. اسکریپت `deploy/deploy.sh` برای همین جریان آماده شده است.

| مرحله | دلیل |
| --- | --- |
| Backup پیش از انتشار | امکان بازیابی در صورت شکست جدی |
| دریافت نسخه جدید کد | همگام‌سازی مخزن با نسخه هدف |
| Build مجدد Imageها | اعمال تغییرهای برنامه و dependencyها |
| Migration | به‌روزرسانی ساختار پایگاه‌داده |
| Collectstatic | آماده شدن فایل‌های Static |
| Restart سرویس‌های اپلیکیشن | اجرای نسخه جدید (`web`، Celery) |
| Reload Nginx | تازه‌سازی DNS داخلی upstream پس از recreate شدن `web` |
| Health Check | بررسی زنده بودن سرویس از طریق gateway |
| Smoke Test | بررسی مسیرهای اصلی پس از انتشار |

فرمان `./deploy/deploy.sh update` سرویس `web` را با `--force-recreate` بازمی‌سازد. در شبکه Docker، کانتینر جدید معمولاً IP داخلی جدیدی می‌گیرد. Nginx نام `web:8000` را در زمان start/reload resolve می‌کند و تا reload بعدی همان IP را نگه می‌دارد؛ بدون reload ممکن است موقتاً به IP قدیمی وصل شود و `502 Bad Gateway` برگرداند. اسکریپت پس از recreate شدن `web`، Nginx را reload می‌کند و سپس health check را اجرا می‌کند.

نمونه جریان به‌روزرسانی:

```bash
./deploy/backup.sh all
git pull
./deploy/deploy.sh update
./deploy/healthcheck.sh
```

# 14- Rollback

Rollback باید با توجه به نوع مشکل انتخاب شود. اگر مشکل فقط در کد برنامه باشد و پایگاه‌داده سالم مانده باشد، معمولاً بازگشت به نسخه کد سالم و اجرای دوباره استقرار کافی است. اگر Migration یا داده‌های پایگاه‌داده آسیب دیده باشد، تصمیم Restore باید با احتیاط و بر اساس `docs/BACKUP_RESTORE.md` انجام شود.

| سناریو | راهبرد کلی |
| --- | --- |
| خطای کد بدون آسیب به داده | بازگشت به Git ref سالم و اجرای `./deploy/deploy.sh update` |
| شکست Migration بدون تغییر داده زنده | بررسی لاگ، اصلاح علت و اجرای مجدد Migration |
| فساد داده یا Migration مخرب | استفاده کنترل‌شده از Restore طبق `docs/BACKUP_RESTORE.md` |
| وجود سفارش‌های جدید پس از Backup | پرهیز از Restore پایگاه‌داده مگر با پذیرش ریسک از دست رفتن داده |
| مشکل Static یا Media | بررسی Collectstatic، Volumeها و تنظیمات Nginx |

Rollback نباید به صورت عجولانه و بدون بررسی اثر روی سفارش‌ها و پرداخت‌های واقعی انجام شود.

# 16- خطاهای متداول

| خطا | نشانه | اقدام ایمن |
| --- | --- | --- |
| نبود `.env` | `deploy.sh` قبل از اجرا خطا می‌دهد | ساخت `.env` از `.env.example` و تنظیم مقدارهای واقعی |
| مقدار `DEBUG=True` | اجرای production settings رد می‌شود | تنظیم `DEBUG=False` |
| نبود `POSTGRES_PASSWORD` | سرویس Database یا preflight شکست می‌خورد | تنظیم password قوی در `.env` |
| Database unavailable | `/ready/` مقدار ready نمی‌دهد | بررسی سرویس `db` و لاگ PostgreSQL |
| Redis unavailable | Readiness یا Celery خطا می‌دهد | بررسی سرویس `redis` و مقدارهای `REDIS_URL` و `CELERY_BROKER_URL` |
| Migration failure | `deploy.sh migrate` شکست می‌خورد | توقف انتشار، بررسی traceback و عدم اجرای Restore بدون تصمیم فنی |
| Static files missing | CSS یا JavaScript بارگذاری نمی‌شود | اجرای `./deploy/deploy.sh collectstatic` و بررسی Nginx/Volume |
| Media files missing | تصاویر محصول یا فایل‌های آپلودی دیده نمی‌شوند | بررسی `media_volume` و مسیرهای Nginx |
| `502` پس از `update` | Nginx بالاست ولی سایت از gateway خطا می‌دهد؛ `/health/` داخل `web` سالم است | بررسی لاگ Nginx برای `connect() failed` به IP قدیمی؛ `docker compose ... exec nginx nginx -s reload` یا اجرای دوباره `./deploy/deploy.sh update` |
| SSL issue | سایت روی HTTPS باز نمی‌شود | بررسی DNS، پورت‌های `80/443`، `CERTBOT_EMAIL` و خروجی `deploy/init-ssl.sh` |
| Admin inaccessible | ورود به پنل یا مسیر `/admin/` مشکل دارد | بررسی Superuser، `ALLOWED_HOSTS`، CSRF و لاگ Web |
| Payment callback issue | پرداخت موفق در سایت نهایی نمی‌شود | بررسی `ZARINPAL_CALLBACK_URL`، `SITE_URL` و لاگ‌های `crumbs.payments` |

# 17- پرسش‌های متداول

## 17-1- آیا این سند جایگزین runbook است؟

خیر. این سند چارچوب استقرار را توضیح می‌دهد. اجرای دقیق روی سرور در `docs/VPS_LAUNCH_RUNBOOK.md` آمده است.

## 17-2- چرا ابتدا HTTP و بعد HTTPS راه‌اندازی می‌شود؟

زیرا Certbot برای صدور گواهی به پاسخ‌گویی دامنه روی پورت `80` نیاز دارد. پس ابتدا سرویس روی HTTP بالا می‌آید، سپس SSL فعال می‌شود.

## 17-3- آیا `.env` باید در مخزن commit شود؟

خیر. `.env` شامل secretها و تنظیمات محیط تولید است و نباید وارد Git شود.

## 17-4- تفاوت `/health/` و `/ready/` چیست؟

`/health/` زنده بودن فرآیند Web را بررسی می‌کند. `/ready/` وابستگی‌هایی مانند Database، Redis، Broker و Migrationها را هم بررسی می‌کند.

## 17-5- آیا Sentry اجباری است؟

خیر. اگر `SENTRY_DSN` خالی باشد، Sentry غیرفعال می‌ماند و برنامه بدون خطای startup اجرا می‌شود.

## 17-6- چه زمانی باید Backup گرفته شود؟

پیش از هر انتشار و به صورت دوره‌ای. دستور اصلی `./deploy/backup.sh all` است و نسخه‌ای از خروجی باید خارج از سرور نگهداری شود.

## 17-7- آیا Restore برای هر Rollback لازم است؟

خیر. Restore فقط برای سناریوهای آسیب‌دیدگی داده یا نیاز واقعی به بازگشت داده استفاده می‌شود. برای خطای کد، معمولاً Rollback کد کافی است.

## 17-8- فایل‌های Static کجا سرو می‌شوند؟

خروجی Collectstatic در `static_volume` قرار می‌گیرد و Nginx آن را از مسیر تنظیم‌شده سرو می‌کند.

## 17-9- فایل‌های Media چگونه پشتیبان‌گیری می‌شوند؟

اسکریپت `deploy/backup.sh media` محتوای Media را به archive فشرده در `backups/media/` تبدیل می‌کند.

## 17-10- اگر پرداخت آنلاین کار نکرد از کجا شروع کنیم؟

ابتدا مقدارهای `DEFAULT_PAYMENT_PROVIDER`، `ZARINPAL_MERCHANT_ID`، `ZARINPAL_CALLBACK_URL` و `SITE_URL` را بررسی کنید. سپس لاگ‌های Web و Sentry را ببینید.

# 18- جمع‌بندی

استقرار Crumbs بر پایه Docker Compose، تفکیک سرویس‌ها، تنظیمات production، Health/Readiness، Backup، Restore و مانیتورینگ طراحی شده است. کد پروژه برای اجرای production آماده است، اما موفقیت Go Live به تنظیم درست سرور، دامنه، secretها، SSL، پرداخت، پیامک، Backup و تست‌های پس از استقرار وابسته است.

این سند باید همراه با runbook استقرار، چک‌لیست Go Live، برنامه تست Launch، مستند Backup/Restore و مستند Observability استفاده شود. هیچ‌کدام از این سندها به‌تنهایی جایگزین کنترل عملیاتی کامل پیش از راه‌اندازی واقعی نیستند.
