# 1- مقدمه

این سند راهنمای عملیاتی مدیریت Crumbs است. هدف آن این است که مالک کافه، مدیر فروشگاه، صندوق‌دار، نیروی آشپزخانه و نیروی کانتر بتوانند کارهای روزانه سایت و سفارش‌ها را بدون دانش برنامه‌نویسی انجام دهند.

این سند راهنمای توسعه نرم‌افزار نیست. بنابراین فقط در موارد ضروری از نام‌های فنی مانند مسیرهای پنل یا مقدارهای وضعیت استفاده شده است؛ آن هم برای اینکه کاربران عملیاتی بدانند دقیقاً کدام صفحه یا وضعیت را باید بررسی کنند.

## 1-1- چه کسانی باید از این راهنما استفاده کنند

| نقش | استفاده اصلی از این سند |
| --- | --- |
| مالک کافه | نظارت بر فروش، سفارش‌ها، دسترسی کارکنان، کوپن‌ها، گزارش شیفت و وضعیت کلی عملیات. |
| مدیر فروشگاه | مدیریت روزانه محصولات، موجودی، سفارش‌ها، پرداخت‌های مشکل‌دار و چک‌لیست‌های شروع/پایان شیفت. |
| صندوق‌دار | ثبت پرداخت حضوری، بررسی سفارش‌های در انتظار پرداخت و کمک به مشتری در پیدا کردن سفارش. |
| نیروی آشپزخانه | استفاده از صف آشپزخانه برای شروع آماده‌سازی و آماده تحویل کردن سفارش. |
| نیروی کانتر | مشاهده سفارش‌های آماده، تطبیق شماره سفارش و ثبت تحویل. |

## 1-2- تفاوت پنل مدیریت Django و صفحات عملیاتی

دو نوع صفحه مدیریتی در سیستم وجود دارد:

| نوع صفحه | مسیر نمونه | کاربرد |
| --- | --- | --- |
| پنل مدیریت Django | `/admin/` | مدیریت مدل‌ها مانند محصولات، سفارش‌ها، پرداخت‌ها، موجودی، کاربران، پیامک و کوپن‌ها. |
| صفحات عملیاتی سفارشی | مانند `/admin/kitchen/` و `/admin/pickup-screen/` | کارهای سریع روزانه مثل صف آشپزخانه، تحویل از کانتر، جست‌وجوی سفارش و گزارش شیفت. |

پنل مدیریت برای تغییر داده‌ها و بررسی جزئیات مناسب است. صفحات عملیاتی برای کار روزانه سریع‌تر و ایمن‌تر طراحی شده‌اند.

## 1-3- حساب کاربری کارکنان

برای هر عضو تیم باید حساب جداگانه ساخته شود. استفاده مشترک از یک حساب باعث می‌شود مشخص نباشد چه کسی وضعیت سفارش، پرداخت یا محصول را تغییر داده است.

قوانین مهم:

- رمز عبور `superuser` نباید بین کارکنان به اشتراک گذاشته شود.
- هر کارمند باید فقط دسترسی لازم برای نقش خود را داشته باشد.
- حساب کارکنانی که دیگر در مجموعه فعال نیستند باید سریعاً غیرفعال شود.
- تغییرهای حساس مانند پرداخت، موجودی و دسترسی کاربران باید فقط توسط افراد مجاز انجام شود.

# 2- دسترسی و ورود

## 2-1- مسیر ورود

| مورد | مقدار |
| --- | --- |
| مسیر پنل مدیریت | `/admin/` |
| عنوان پنل | `مدیریت Crumbs` |
| عنوان مرورگر | `پنل مدیریت Crumbs` |
| عنوان داشبورد | `داشبورد مدیریت` |

برای ورود باید نام کاربری و رمز عبور معتبر داشته باشید. هیچ `credential` واقعی نباید در این سند، پیام‌رسان‌ها یا فایل‌های عمومی نوشته شود.

## 2-2- شرط دسترسی کارکنان

برای ورود به پنل مدیریت، حساب کاربر باید `staff` باشد. در `Django Admin` این معمولاً با گزینه `is_staff` کنترل می‌شود.

| نوع حساب | کاربرد |
| --- | --- |
| Superuser | دسترسی کامل به همه بخش‌ها. فقط برای مالک فنی یا مدیر بسیار محدود استفاده شود. |
| Staff | دسترسی به بخش‌هایی که برای نقش کارمند مجاز شده است. |
| Customer user | حساب مشتری؛ برای ورود به پنل مدیریت کافی نیست. |

## 2-3- خروج از پنل

پس از پایان کار، از گزینه خروج در پنل مدیریت استفاده کنید. اگر با سیستم مشترک کار می‌کنید، بستن مرورگر به‌تنهایی کافی نیست.

## 2-4- ایمنی رمز عبور

| کار ایمن | کار ناایمن |
| --- | --- |
| استفاده از رمز عبور اختصاصی برای هر فرد | استفاده مشترک از رمز `superuser` |
| تغییر رمز پس از خروج کارمند از تیم | ارسال رمز در پیام‌رسان عمومی |
| استفاده از مرورگر به‌روز | ذخیره رمز روی کامپیوتر عمومی |
| خروج از پنل بعد از پایان شیفت | باز گذاشتن پنل روی سیستم کانتر |

## 2-5- مرورگر پیشنهادی

از مرورگرهای به‌روز مانند Chrome، Firefox، Safari یا Edge استفاده کنید. برای سیستم‌های کانتر و آشپزخانه بهتر است یک مرورگر اختصاصی برای پنل باز باشد و `tab`های غیرمرتبط در همان `session` استفاده نشود.

## 2-6- اگر ورود ناموفق بود

| نشانه | اقدام ایمن |
| --- | --- |
| رمز عبور اشتباه است | از مدیر دارای دسترسی درخواست `reset` رمز کنید. |
| پیام عدم دسترسی به پنل دیده می‌شود | بررسی شود حساب کاربر `staff` باشد و `permission` لازم داشته باشد. |
| صفحه `admin` باز نمی‌شود | اتصال اینترنت، آدرس دامنه و وضعیت سرویس را بررسی کنید؛ اگر ادامه داشت با مسئول فنی تماس بگیرید. |
| همه کارکنان نمی‌توانند وارد شوند | احتمال مشکل سرویس، تنظیمات دامنه یا Readiness وجود دارد؛ escalation فنی لازم است. |

# 3- نمای کلی پنل مدیریت

## 3-1- بخش‌های اصلی

پنل مدیریت Crumbs فارسی‌سازی شده است. کاربران و گروه‌ها در بخش `احراز هویت` با عنوان‌های `کاربران` و `گروه‌ها` دیده می‌شوند. برخی app labelهای داخلی با نام پوشه متفاوت‌اند: بخش پیامک با label `sms` و بخش تحویل/ارسال `legacy` با label `fulfillment` ثبت شده است.

| بخش | مدل‌ها/صفحات مهم | کاربرد عملیاتی |
| --- | --- | --- |
| Products | `دسته‌بندی‌ها`، `محصولات` | مدیریت کاتالوگ، قیمت، تصویر، وضعیت نمایش و محصولات ویژه. |
| Orders | `سفارش‌ها` | مشاهده سفارش، وضعیت، اقلام، پرداخت، رسید و actionهای عملیاتی. |
| Payments | `پرداخت‌ها`، `رویدادهای پرداخت` | بررسی پرداخت‌ها، `provider`، وضعیت، مبلغ، eventها و خطاهای پرداخت. |
| Inventory | `موجودی محصولات`، `ظرفیت‌های تولید روزانه`، `رزروهای موجودی` | کنترل stock، ظرفیت روزانه و رزروها. |
| Careers | `درخواست‌های همکاری` | بررسی درخواست‌های شغلی، رزومه و وضعیت HR. |
| Growth | کوپن‌ها، معرفی‌ها، قوانین پروموشن، سبدهای رها شده، رویدادهای رشد، snapshotها | مدیریت کوپن و مشاهده داده‌های رشد. |
| Loyalty | `حساب‌های وفاداری`، `تراکنش‌های وفاداری` | مشاهده امتیاز، سطح و تراکنش‌های وفاداری. |
| SMS | `قالب‌های پیامک`، `لاگ‌های پیامک` | مدیریت قالب و بررسی ارسال/شکست پیامک. |
| Users | `کاربران`، `گروه‌ها`، `آدرس‌ها` | مدیریت دسترسی کارکنان و اطلاعات حساب‌ها. |
| `Core / operations` | `لاگ‌های وظایف پس‌زمینه`، `تصاویر تحلیل روزانه` و صفحات عملیاتی | مشاهده `task`ها، Health عملیاتی و داشبوردها. |

برچسب‌های app در پنل مدیریت به‌صورت فارسی تنظیم شده‌اند:

| app داخلی | عنوان قابل مشاهده |
| --- | --- |
| `products` | محصولات |
| `orders` | سفارش‌ها |
| `payments` | پرداخت‌ها |
| `inventory` | موجودی انبار |
| `careers` | همکاری با ما |
| `growth` | رشد و بازاریابی |
| `loyalty` | باشگاه مشتریان |
| `accounts` | حساب‌ها |
| `core` | هسته |
| `intelligence` | هوش تجاری |
| `cart` | سبد خرید |
| `sms` | پیامک |
| `fulfillment` | تحویل و ارسال |

## 3-2- صفحه لیست

در بیشتر بخش‌ها صفحه لیست شامل این ابزارهاست:

| ابزار | کاربرد |
| --- | --- |
| ستون‌ها | نمایش خلاصه رکوردها مانند شماره سفارش، مشتری، وضعیت، مبلغ و تاریخ. |
| فیلترها | محدود کردن فهرست بر اساس وضعیت، تاریخ، دسته‌بندی، `provider` یا نوع پرداخت. |
| جست‌وجو | پیدا کردن رکورد با شماره سفارش، نام، تلفن، `slug`، کد کوپن یا شناسه `provider`. |
| انتخاب چند ردیف | اجرای `admin` action روی چند رکورد. فقط در موارد مطمئن استفاده شود. |
| لینک تغییر | ورود به فرم جزئیات همان رکورد. |

## 3-3- فرم تغییر

فرم تغییر هر رکورد ممکن است فیلدهای قابل ویرایش و readonly داشته باشد. فیلد readonly برای مشاهده است و نباید با راه‌های غیرمعمول تغییر داده شود.

نمونه readonlyهای مهم:

| بخش | readonlyهای مهم |
| --- | --- |
| سفارش | `order_number`، `daily_sequence`، `payment_status`، مبالغ، کوپن، تاریخ‌ها. |
| پرداخت | order، `provider`، status، amount، currency، شناسه `provider`، لینک پرداخت، metadata امن. |
| موجودی محصول | `reserved_quantity`، `available_display`، `updated_at`. |
| رزرو موجودی | زمان‌های ایجاد/به‌روزرسانی؛ تغییر مستقیم رزرو عملیاتی توصیه نمی‌شود. |
| درخواست همکاری | `created_at` و نمایش پاسخ‌های HR. |
| لاگ پیامک | فیلدهای ارسال و وضعیت readonly هستند. |
| تراکنش وفاداری | اطلاعات تراکنش readonly است. |

## 3-4- Admin actions

`Admin` actionها برای انجام عملیات کنترل‌شده هستند. برای سفارش‌ها، این actionها از سرویس‌های کسب‌وکار استفاده می‌کنند و امن‌تر از تغییر دستی فیلد status هستند.

قانون عملیاتی: اگر action وجود دارد، همان action را استفاده کنید و از تغییر دستی `status/payment` status خودداری کنید.

# 4- عملیات روزانه

## 4-1- شروع شیفت

| مرحله | مسیر/بخش | اقدام |
| --- | --- | --- |
| 1 | `/admin/` | با حساب شخصی `staff` وارد شوید. |
| 2 | `/health/` و در صورت مسئولیت فنی `/ready/` | اگر مدیر مسئول وضعیت سیستم است، سلامت سرویس را بررسی کند. |
| 3 | `/admin/operations/` | سفارش‌های جدید، پرداخت‌های حضوری در انتظار، موجودی کم، payment issue و `task`های شکست‌خورده را ببینید. |
| 4 | `/admin/ops/` | موارد عملیاتی مثل محصولات بدون موجودی، پرداخت‌های stale و وضعیت زرین‌پال را بررسی کنید. |
| 5 | `/admin/kitchen/` | صف آشپزخانه را برای سفارش‌های آماده پردازش کنترل کنید. |
| 6 | `/admin/pickup-screen/` | سفارش‌های آماده تحویل از شیفت قبل را بررسی کنید. |

## 4-2- حین سرویس

| نقش | کارهای اصلی |
| --- | --- |
| مدیر شیفت | پایش `/admin/operations/` و `/admin/ops/`، رسیدگی به خطاهای پرداخت، کنترل موجودی کم. |
| صندوق‌دار | بررسی سفارش‌های `awaiting_payment` و ثبت دریافت پرداخت حضوری از action مناسب سفارش. |
| آشپزخانه | استفاده از `/admin/kitchen/` برای شروع آماده‌سازی و آماده تحویل کردن سفارش. |
| کانتر | استفاده از `/admin/pickup-screen/` برای تحویل سفارش‌های `packaged`. |
| همه نقش‌های عملیاتی مجاز | استفاده از `/admin/order-lookup/` برای پیدا کردن سفارش مشتری. |

## 4-3- پایان شیفت

| مرحله | مسیر/بخش | اقدام |
| --- | --- | --- |
| 1 | `/admin/shift-summary/` | گزارش فروش، تعداد سفارش، روش‌های پرداخت، محصولات پرفروش، موجودی کم و payment issueها را مرور کنید. |
| 2 | `/admin/order-lookup/` یا لیست سفارش‌ها | سفارش‌های حل‌نشده، در انتظار پرداخت یا آماده تحویل را بررسی کنید. |
| 3 | Payments | پرداخت‌های `failed`، `pending` یا `processing` غیرعادی را ثبت و پیگیری کنید. |
| 4 | SMS `logs` | پیامک‌های `failed` را بررسی کنید. |
| 5 | backups | فقط اگر مسئولیت عملیاتی backup دارید، وضعیت اجرای backup را با مسئول فنی/زیرساخت تأیید کنید. |

# 5- مدیریت محصولات

## 5-1- بخش‌های محصول در پنل

| بخش | مسیر `admin` | کاربرد |
| --- | --- | --- |
| دسته‌بندی‌ها | `/admin/products/category/` | ساخت و ویرایش دسته‌بندی فروشگاه. |
| محصولات | `/admin/products/product/` | ساخت و ویرایش محصول، قیمت، تصویر، وضعیت نمایش و ویژه بودن. |

## 5-2- ساخت دسته‌بندی

1. وارد `/admin/products/category/` شوید.
2. گزینه افزودن دسته‌بندی را انتخاب کنید.
3. `name` را وارد کنید.
4. `slug` را بررسی کنید. اگر خالی باشد سیستم از نام دسته‌بندی `slug` می‌سازد، اما برای `URL`های تمیز بهتر است مقدار کوتاه و انگلیسی باشد.
5. در صورت نیاز `description` و `image` را وارد کنید.
6. ذخیره کنید.

ستون‌های مهم لیست دسته‌بندی:

| ستون | معنی |
| --- | --- |
| `name` | نام دسته‌بندی. |
| `slug` | بخش `URL` دسته‌بندی. |
| `تعداد محصول` | تعداد محصولات داخل دسته. |
| `پیش‌نمایش` | تصویر دسته‌بندی در صورت وجود. |

## 5-3- ساخت محصول

1. وارد `/admin/products/product/` شوید.
2. گزینه افزودن محصول را انتخاب کنید.
3. در بخش `اطلاعات اصلی`، دسته، نام، `slug`، توضیحات و مواد اولیه را وارد کنید.
4. در بخش `قیمت و فروش`، قیمت، وضعیت موجودی و گزینه ویژه را تنظیم کنید.
5. در بخش `تصویر و رسانه`، تصویر محصول را بارگذاری کنید.
6. پیش‌نمایش تصویر را بررسی کنید.
7. ذخیره کنید.

فیلدهای محصول:

| فیلد | برچسب/معنی | راهنمای عملیاتی |
| --- | --- | --- |
| `category` | دسته‌بندی | باید قبل از ساخت محصول وجود داشته باشد. |
| `name` | نام محصول | نامی که در سایت و سفارش‌ها دیده می‌شود. |
| `slug` | نامک | بخش `URL` محصول؛ در هر دسته باید یکتا باشد. |
| `description` | توضیحات | توضیح محصول برای مشتری. |
| `ingredients` | مواد اولیه | مواد یا توضیحات تکمیلی. |
| `price` | قیمت | مقدار فروش محصول. از قیمت صفر یا منفی استفاده نکنید. |
| `image` | تصویر | تصویر محصول. |
| `availability_status` | وضعیت موجودی | `available`، `out_of_stock` یا `coming_soon`. |
| `is_featured` | ویژه | محصولات ویژه در صفحه اصلی استفاده می‌شوند. |
| `created_at`، `updated_at` | تاریخ‌ها | readonly هستند. |

در مدل فعلی فیلد جداگانه‌ای برای ترتیب نمایش دستی وجود ندارد. ترتیب محصولات بر اساس ویژه بودن و نام محصول است.

## 5-4- وضعیت نمایش محصول

| مقدار فنی | نمایش فارسی در `admin` | اثر عملیاتی |
| --- | --- | --- |
| `available` | فعال | محصول در فهرست فروشگاه و sitemap محصول قابل نمایش است و می‌تواند به سبد اضافه شود. |
| `out_of_stock` | ناموجود | محصول نباید به‌عنوان قابل فروش در جریان اصلی استفاده شود. |
| `coming_soon` | به‌زودی | برای معرفی محصول بدون فروش فعال. |

## 5-5- ویرایش محصول

برای تغییر قیمت، توضیح، تصویر یا وضعیت، وارد فرم محصول شوید و تغییر را ذخیره کنید. پس از ذخیره یا حذف محصول/دسته‌بندی، `cache` کاتالوگ توسط `admin` invalidation به‌روزرسانی می‌شود.

## 5-6- غیرفعال کردن به جای حذف

برای محصولی که موقتاً فروش ندارد:

1. محصول را باز کنید.
2. `availability_status` را روی `out_of_stock` یا `coming_soon` بگذارید.
3. ذخیره کنید.

حذف محصول توصیه نمی‌شود، چون محصول ممکن است در سفارش‌های قبلی استفاده شده باشد. مدل `OrderItem.product` با `PROTECT` محافظت شده است.

## 5-7- توصیه‌های تصویر

| مورد | توصیه |
| --- | --- |
| وضوح | تصویر واضح و واقعی از محصول استفاده شود. |
| نسبت تصویر | برای کارت محصول بهتر است تصاویر هم‌نسبت باشند. |
| حجم فایل | از فایل بسیار سنگین استفاده نکنید. |
| نام فایل | نام فایل بدون اطلاعات حساس یا نام مشتری باشد. |

## 5-8- خطاهای رایج محصول

| خطا | نتیجه | اقدام درست |
| --- | --- | --- |
| `slug` تکراری در همان دسته | ذخیره با خطا مواجه می‌شود. | `slug` را یکتا کنید. |
| محصول بدون دسته | در مدل فعلی دسته الزامی است. | ابتدا دسته‌بندی بسازید. |
| قیمت اشتباه | مبلغ سفارش اشتباه می‌شود. | قبل از فعال کردن محصول قیمت را بازبینی کنید. |
| حذف محصول قدیمی | ممکن است به سفارش‌های قبلی وابسته باشد. | به جای حذف، وضعیت را ناموجود کنید. |
| تصویر نامناسب | تجربه مشتری ضعیف می‌شود. | تصویر واضح و هماهنگ بارگذاری کنید. |

## 6-4- معنی رزرو

رزرو یعنی سیستم برای یک `cart` یا order، بخشی از موجودی/ظرفیت را موقتاً کنار گذاشته است تا فروش همزمان باعث oversell نشود.

وضعیت‌های رزرو:

| مقدار | معنی |
| --- | --- |
| `active` | رزرو فعال است. |
| `confirmed` | پرداخت موفق یا دریافت حضوری تأیید شده و رزرو قطعی شده است. |
| `released` | رزرو آزاد شده است. |
| `expired` | رزرو منقضی شده است. |

هشدار مهم: رزروها را دستی تغییر ندهید، مگر اینکه یک توسعه‌دهنده یا فرآیند بازیابی مستند، آن را مشخصاً درخواست کرده باشد.

## 6-5- به‌روزرسانی امن stock

1. محصول را در `/admin/inventory/productinventory/` پیدا کنید.
2. فقط `stock_quantity`، `low_stock_threshold`، `track_stock` یا `allow_preorder` را در صورت نیاز تغییر دهید.
3. `reserved_quantity` و `available_display` را دستکاری نکنید.
4. پس از ذخیره، داشبورد عملیات را بررسی کنید.

## 6-6- وقتی موجودی به صفر می‌رسد

هنگام تکمیل سفارش و مصرف رزرو، اگر موجودی قابل فروش محصول به صفر برسد، سیستم می‌تواند وضعیت محصول را به `out_of_stock` تغییر دهد. مدیر باید محصول و موجودی را بررسی کند و پس از شارژ مجدد stock، وضعیت محصول را در صورت نیاز به `available` برگرداند.

# 8- جریان پرداخت حضوری

## 8-1- پرداخت حضوری از دید مشتری

در `checkout` عمومی سایت، مشتری یک گزینه با عنوان «پرداخت حضوری» می‌بیند. این گزینه در سیستم با روش `cash` ثبت می‌شود. مشتری می‌تواند در کافه مبلغ را نقدی یا با کارت پرداخت کند، اما ثبت سیستمی سفارش عمومی فعلی از مسیر پرداخت حضوری انجام می‌شود.

## 8-2- سفارش پرداخت حضوری چگونه دیده می‌شود

| فیلد | مقدار معمول |
| --- | --- |
| `status` | `awaiting_payment` |
| `payment_status` | `pending_payment` |
| `payment_method` | `cash` |
| Payment `provider` | `cash` |
| Payment status | `pending` |

این سفارش‌ها در داشبورد عملیات و `task` center در بخش پرداخت حضوری در انتظار دیده می‌شوند.

## 8-3- ثبت دریافت وجه

1. وارد `/admin/orders/order/` شوید یا از `/admin/operations/` سفارش را پیدا کنید.
2. سفارش را بررسی کنید: شماره سفارش، نام مشتری، مبلغ، اقلام و روش پرداخت.
3. مبلغ را در کافه دریافت کنید.
4. در لیست سفارش، سفارش را انتخاب کنید.
5. action `ثبت دریافت نقد (صندوق)` را اجرا کنید.
6. وضعیت سفارش پس از تأیید پرداخت به مسیر آماده‌سازی منتقل می‌شود.

اگر سفارش به‌صورت داخلی با روش `counter_card` ساخته شده باشد، action `ثبت دریافت کارت (صندوق)` برای آن وجود دارد. برای سفارش عمومی پرداخت حضوری، پیش‌فرض عملیاتی `cash` است.

## 8-4- بعد از تأیید پرداخت حضوری چه اتفاقی می‌افتد

| مرحله | نتیجه |
| --- | --- |
| Payment ثبت می‌شود | وضعیت Payment به `succeeded` می‌رسد. |
| موجودی تأیید می‌شود | رزروهای سفارش confirmed می‌شوند. |
| سفارش وارد آماده‌سازی می‌شود | status به `preparing` منتقل می‌شود. |
| سفارش در آشپزخانه دیده می‌شود | در `/admin/kitchen/` قابل پیگیری است. |

<a id="sec-9"></a>

# 9- جریان پرداخت آنلاین

## 9-1- وضعیت‌های پرداخت آنلاین

| وضعیت Payment | معنی |
| --- | --- |
| `pending` | پرداخت ایجاد شده اما هنوز `session` درگاه کامل نشده است. |
| `processing` | کاربر به درگاه هدایت شده یا `checkout` فعال است. |
| `succeeded` | پرداخت توسط `provider` تأیید شده است. |
| `failed` | پرداخت شکست خورده یا تأیید نشده است. |
| `cancelled` | پرداخت لغو شده است. |
| `refunded` | پرداخت مسترد شده است. |

## 9-2- مسیر پرداخت آنلاین

1. مشتری در `checkout` گزینه پرداخت آنلاین را انتخاب می‌کند.
2. سیستم سفارش را می‌سازد و موجودی را برای سفارش رزرو می‌کند.
3. Payment آنلاین ساخته می‌شود و مشتری به درگاه هدایت می‌شود.
4. `callback` زرین‌پال در `/payments/zarinpal/callback/` پرداخت را بررسی می‌کند.
5. اگر پرداخت موفق باشد، سفارش به `paid` و سپس `confirmed_by_shop` می‌رسد.
6. اگر پرداخت شکست بخورد، سفارش cancel و رزروها آزاد می‌شوند.

## 9-3- ایمنی callback تکراری

سیستم `callback` تکراری پرداخت موفق را نادیده می‌گیرد و سفارش پرداخت‌شده را دوباره تغییر نمی‌دهد. همچنین پرداخت زرین‌پال `processing` قابل استفاده مجدد است تا `checkout` تکراری غیرضروری ساخته نشود.

## 9-4- پاک‌سازی پرداخت stale

پرداخت آنلاین `pending` یا `processing` برای `provider`های زرین‌پال و Stripe اگر بعد از ۳۰ دقیقه کامل نشود، توسط `task` دوره‌ای cleanup بررسی می‌شود. در صورت stale بودن، payment شکست‌خورده می‌شود، سفارش لغو می‌شود و رزروها آزاد می‌شوند.

## 9-5- چه کاری انجام ندهید

| کار | دلیل ممنوعیت |
| --- | --- |
| پرداخت آنلاین را دستی موفق نکنید | موفقیت باید از `provider` تأیید شود. |
| status پرداخت را برای حل سریع مشکل تغییر ندهید | ممکن است پول واقعاً دریافت نشده باشد. |
| سفارش آنلاین ناموفق را بدون بررسی مالی آماده نکنید | باعث تحویل بدون پرداخت می‌شود. |
| `callback` یا event خام را حذف نکنید | برای بررسی مالی و فنی لازم است. |

## 9-6- شناسایی مشکل پرداخت

از این بخش‌ها استفاده کنید:

| مسیر/بخش | کاربرد |
| --- | --- |
| `/admin/operations/` | مشاهده payment issueهای فوری. |
| `/admin/ops/` | مشاهده `failed` `payments` و stale `online` `payments`. |
| `/admin/payments/payment/` | بررسی جزئیات Payment. |
| `/admin/payments/paymentevent/` | بررسی رویداد `provider`. |

اگر مشتری می‌گوید پول کم شده اما سفارش به‌روزرسانی نشده است، سفارش را تحویل ندهید. شماره سفارش، شماره روزانه، نام مشتری، مبلغ و زمان پرداخت را ثبت کنید و به مسئول فنی/مالی ارجاع دهید.

# 11- صفحه تحویل از کانتر

## 11-1- مسیر

| مورد | مقدار |
| --- | --- |
| مسیر | `/admin/pickup-screen/` |
| action route | `/admin/pickup-screen/action/` |
| دسترسی | `staff` |

## 11-2- چه سفارش‌هایی نمایش داده می‌شوند

فقط سفارش‌هایی نمایش داده می‌شوند که:

| فیلد | مقدار |
| --- | --- |
| `status` | `packaged` |
| `payment_status` | `paid`، `cod_confirmed` یا `cash_received` |

## 11-3- تحویل سفارش

1. از مشتری شماره سفارش کامل یا شماره روزانه را بگیرید.
2. سفارش را در صفحه `pickup` یا order lookup پیدا کنید.
3. نام مشتری، شماره تماس یا اقلام سفارش را برای اطمینان تطبیق دهید.
4. بررسی کنید پرداخت معتبر باشد.
5. action `mark_picked_up` را اجرا کنید.
6. سیستم سفارش را از مسیر completion به `delivered` می‌رساند.

## 11-4- جلوگیری از تحویل تکراری

اگر سفارش قبلاً `delivered` شده باشد، دوباره تحویل ندهید. پیام سیستم ممکن است نشان دهد سفارش already picked up است. در صورت ابهام با مدیر شیفت هماهنگ کنید.

## 11-5- اگر مشتری شماره سفارش ندارد

از `/admin/order-lookup/` استفاده کنید و با تلفن، نام، نام خانوادگی، شماره روزانه یا یادداشت/شماره میز جست‌وجو کنید. اگر چند سفارش مشابه وجود دارد، مبلغ، اقلام، زمان ثبت و شماره تماس را با مشتری تطبیق دهید.

| `console` | `provider` توسعه/محیط غیرتولیدی؛ ارسال واقعی بیرونی انجام نمی‌دهد. |
| `kavenegar` | `provider` تولیدی پیامک؛ نیازمند `credential` واقعی است. |

برای ارسال واقعی پیامک در تولید، `KAVENEGAR_API_KEY` و تنظیمات مرتبط باید توسط مسئول فنی در محیط production تنظیم شود. کارکنان نباید `credential` پیامک را در پنل یا فایل‌ها وارد کنند.

## 18-5- quiet hours، rate limit و retry

| قابلیت | رفتار |
| --- | --- |
| Quiet hours | پیامک‌های غیرتراکنشی در بازه سکوت skip می‌شوند. |
| Rate limit | محدودیت تعداد پیامک روزانه برای `user/recipient` اعمال می‌شود. |
| Dedupe | پیامک تکراری در بازه مشخص ارسال نمی‌شود. |
| Retry `failed` SMS | `task` `retry_failed_sms_task` هر ۳۰ دقیقه پیامک‌های `failed` را تا سقف تلاش مشخص `retry` می‌کند. |

کارکنان می‌توانند لاگ‌ها، status و error message را ببینند. تغییر `provider`، کلیدهای Kavenegar و تنظیمات rate limit نیازمند دسترسی فنی است.

# 19- کاربران و مجوزها

## 19-1- ساخت کاربر staff

1. وارد `/admin/auth/user/` شوید.
2. کاربر جدید بسازید یا کاربر موجود را باز کنید.
3. اطلاعات هویتی و ایمیل را تکمیل کنید.
4. گزینه `staff` status را فقط برای افراد مجاز فعال کنید.
5. به جای `superuser` کردن، `permissions` لازم را به کاربر یا گروه بدهید.
6. ذخیره کنید.

## 19-2- حداقل دسترسی لازم

| نقش | دسترسی پیشنهادی |
| --- | --- |
| آشپزخانه | دسترسی به kitchen queue و مشاهده سفارش‌های لازم؛ عدم دسترسی به پرداخت و کاربران. |
| کانتر | `pickup` screen، order lookup و مشاهده سفارش‌های لازم. |
| صندوق‌دار | مشاهده سفارش، ثبت پرداخت حضوری، order lookup و مشاهده paymentهای لازم. |
| مدیر فروشگاه | محصولات، موجودی، سفارش‌ها، پرداخت‌ها، گزارش شیفت و داشبوردهای عملیاتی. |
| مالک/مدیر ارشد | مدیریت users، `permissions`، کوپن‌ها و بخش‌های حساس. |

این جدول راهنمای عملیاتی است؛ تنظیم دقیق `permission` باید توسط فرد آشنا با `Django Admin` و نیازهای مجموعه انجام شود.

## 19-3- محدودیت superuser

همه کارکنان نباید `superuser` باشند. `superuser` می‌تواند به همه اطلاعات و عملیات حساس دسترسی داشته باشد.

## 19-4- خروج کارکنان از مجموعه

1. حساب کاربر را پیدا کنید.
2. `staff` status یا `active` بودن را بر اساس سیاست مجموعه غیرفعال کنید.
3. دسترسی گروه‌ها و `permissions` را حذف کنید.
4. اگر کاربر به رمزهای مشترک دسترسی داشته، رمزها را تغییر دهید.
5. موضوع را در گزارش مدیریتی ثبت کنید.

# 24- پرسش‌های پرتکرار

## چرا یک محصول برای مشتری قابل خرید نیست؟

احتمالاً وضعیت محصول `out_of_stock` یا `coming_soon` است، یا موجودی قابل فروش صفر شده است. محصول را در Products و موجودی را در Inventory بررسی کنید.

## چرا stock رزروشده است؟

وقتی محصول وارد سبد خرید یا سفارش می‌شود، سیستم برای جلوگیری از فروش بیش از موجودی، آن مقدار را رزرو می‌کند. رزرو ممکن است `active`، confirmed، released یا `expired` باشد.

## چرا سفارش در انتظار پرداخت است؟

اگر status برابر `awaiting_payment` باشد، مشتری پرداخت حضوری را انتخاب کرده و صندوق هنوز دریافت وجه را ثبت نکرده است. اگر status برابر `pending_payment` باشد، معمولاً پرداخت آنلاین هنوز کامل نشده است.

## آیا می‌توانم پرداخت آنلاین را دستی paid کنم؟

خیر. پرداخت آنلاین باید از مسیر `provider` و `callback` تأیید شود. اگر مشتری مدعی پرداخت موفق است اما سیستم به‌روز نشده، موضوع باید به مسئول فنی/مالی ارجاع شود.

## چطور محصول را غیرفعال کنم؟

محصول را حذف نکنید. در فرم محصول، `availability_status` را روی `out_of_stock` یا `coming_soon` بگذارید و ذخیره کنید.

## چطور سفارش را پیدا کنم؟

از `/admin/order-lookup/` استفاده کنید. می‌توانید با شماره سفارش، شماره روزانه، نام، نام خانوادگی، تلفن یا یادداشت/شماره میز جست‌وجو کنید.

## چرا پیامک ارسال نشده است؟

ممکن است `provider` `console` باشد، `credential` تولیدی تنظیم نشده باشد، شماره وجود نداشته باشد، quiet hours یا rate limit فعال شده باشد، یا `provider` خطا داده باشد. `SMSLog` را بررسی کنید.

## چرا نمی‌توانم درخواست همکاری را حذف کنم؟

حذف کامل درخواست همکاری در `admin` غیرفعال شده است تا داده متقاضی به‌صورت ناخواسته حذف نشود. برای مدیریت فرآیند، status را تغییر دهید.

## چرا سفارش آماده در pickup screen دیده نمی‌شود؟

فقط سفارش‌های `packaged` با payment status معتبر (`paid`، `cod_confirmed` یا `cash_received`) در `pickup` screen دیده می‌شوند. status و payment status سفارش را بررسی کنید.

## چرا action سفارش خطا می‌دهد؟

احتمالاً transition از وضعیت فعلی به وضعیت هدف مجاز نیست یا پیش‌نیاز پرداخت/موجودی کامل نشده است. status فعلی، payment status و پیام خطا را بررسی کنید.

# 25- جمع‌بندی

مدیریت Crumbs باید با حساب‌های شخصی `staff`، دسترسی محدود و استفاده از صفحات عملیاتی انجام شود. مدیر سایت مسئول کنترل محصولات، موجودی، سفارش‌ها، پرداخت‌ها، گزارش شیفت، کاربران و خطاهای عملیاتی است؛ اما نباید کارهای فنی مانند تغییر `.env`، اجرای migration، restore backup یا دستکاری مستقیم پرداخت و رزرو موجودی را انجام دهد.

مرز escalation روشن است:

| موضوع | مسئول معمول |
| --- | --- |
| تغییر محصول، قیمت، وضعیت نمایش و موجودی عادی | مدیر فروشگاه |
| ثبت پرداخت حضوری و تحویل سفارش | صندوق‌دار/کانتر با مجوز لازم |
| آماده‌سازی سفارش | آشپزخانه |
| بررسی گزارش شیفت و خطاهای روزانه | مدیر شیفت/مالک |
| پرداخت آنلاین نامشخص، Readiness failure، `task` `dead`، خطای `provider` و تنظیمات production | مسئول فنی/توسعه‌دهنده |

اصل عملیاتی نهایی: هرجا action رسمی یا صفحه عملیاتی وجود دارد، همان را استفاده کنید؛ از تغییر مستقیم فیلدهای حساس برای دور زدن فرآیند سیستم خودداری کنید.
