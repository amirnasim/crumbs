# 1- مقدمه

این سند راهنمای توسعه Crumbs است. هدف آن این است که توسعه‌دهنده جدید بتواند بدون بازطراحی معماری، در چارچوب فعلی پروژه feature جدید اضافه کند، bug را اصلاح کند، تست بنویسد و تغییرها را به‌صورت قابل نگهداری تحویل دهد.

این سند جایگزین سند معماری نیست. جزئیات کامل معماری در `docs/03-معماری-سیستم.md` قرار دارد. همچنین این سند راهنمای استقرار نیست و جریان production در `docs/06-راهنمای-استقرار.md` توضیح داده شده است.

| کاهش ریسک تغییر | تغییرهای دامنه باید در محل درست انجام شوند تا checkout، پرداخت، موجودی و سفارش آسیب نبینند. |

# 2- معماری توسعه

Crumbs با معماری app-based توسعه داده شده است. هر app مسئول بخشی از دامنه است و منطق حساس در serviceها نگهداری می‌شود. viewها نباید به محل اصلی تصمیم‌های دامنه تبدیل شوند؛ آن‌ها باید request، form، permission و response را مدیریت کنند و mutationهای مهم را به serviceها بسپارند.

## 2-1- ارتباط کلی appها

| app | مسئولیت توسعه‌ای |
| --- | --- |
| `accounts` | حساب کاربری، پروفایل، آدرس و داده اولیه checkout |
| `cart` | سبد خرید، اقلام سبد، merge، lock و mutationهای سبد |
| `careers` | فرم همکاری، اعتبارسنجی رزومه و مدیریت درخواست شغلی |
| `core` | صفحات عمومی، checkout view، SEO، health، dashboards و ابزارهای مشترک |
| `delivery` | state machine سفارش و مدل‌های legacy مربوط به fulfillment |
| `growth` | coupon، referral، promotion، attribution و analytics رشد |
| `intelligence` | داده‌های تحلیلی، توصیه‌گر rule-based و snapshotها |
| `inventory` | موجودی، ظرفیت روزانه، reservation، release و fulfill |
| `loyalty` | امتیاز، tier و تراکنش وفاداری |
| `orders` | سفارش، اقلام سفارش، شماره روزانه، lifecycle و counter checkout |
| `payments` | payment، provider، callback، webhook و idempotency |
| `products` | category، product، قیمت، تصویر و وضعیت عرضه |
| `wishlist` | علاقه‌مندی‌های کاربر |
| `notifications` | SMS template، SMS log، provider و facade اطلاع‌رسانی |

## 2-2- مسئولیت هر لایه

| لایه | مسئولیت | نباید انجام دهد |
| --- | --- | --- |
| Model Layer | تعریف داده، relation، constraint، index و validation نزدیک به داده | اجرای flowهای طولانی کسب‌وکار |
| Service Layer | اجرای business rule، transaction، mutation و orchestration | تولید HTML یا وابستگی مستقیم به request |
| Views | دریافت request، اجرای form، permission، message و redirect | تغییر مستقیم وضعیت سفارش، پرداخت یا موجودی در مسیرهای حساس |
| Forms | اعتبارسنجی ورودی کاربر و تبدیل داده فرم | ذخیره چندمدلی پیچیده بدون service |
| Templates | نمایش داده و partialهای reusable | اجرای منطق دامنه یا query سنگین |
| Admin | مدیریت داده، actionهای امن، readonly fields و فیلترها | دور زدن serviceهای دامنه |
| Celery | اجرای کارهای زمان‌بر، دوره‌ای یا غیرهمزمان | انجام mutation غیر idempotent بدون محافظت |

## 2-3- Service Layer

Service Layer برای بخش‌هایی استفاده می‌شود که تغییر داده، تصمیم دامنه یا وابستگی چند model دارند. نمونه‌های فعلی شامل `OrderService`، `PaymentService`، `CounterCheckoutService`، `CouponService`، `ReferralService`، `SMSService` و توابع service در `inventory.services` هستند.

| ویژگی service خوب | دلیل |
| --- | --- |
| ورودی مشخص | تست‌پذیری و کاهش وابستگی به request |
| خروجی قابل پیش‌بینی | ساده‌تر شدن view و task |
| transaction روشن | جلوگیری از race condition در پرداخت، سفارش و موجودی |
| exception معنادار | نمایش پیام مناسب در view و ثبت لاگ دقیق |
| idempotency در عملیات خارجی | جلوگیری از اثر تکراری callback یا task |

## 2-4- Model Layer

Modelها باید ساختار داده و invariantهای نزدیک به داده را نگهداری کنند. اگر یک قانون به چند model یا چند مرحله وابسته است، بهتر است در service قرار گیرد.

| مورد | محل مناسب |
| --- | --- |
| فیلد، relation، index، constraint | model |
| validation مربوط به یک record | model یا form |
| ساخت سفارش از cart | service |
| تأیید پرداخت و تغییر وضعیت سفارش | service |
| رزرو و آزادسازی موجودی | service |
| transition وضعیت سفارش | `OrderService` و state machine |

## 2-5- Views، Forms، Templates و Admin

| بخش | الگوی توسعه |
| --- | --- |
| Views | ساده، قابل خواندن، کم‌منطق و متکی به form/service |
| Forms | مسئول validation داده ورودی و پیام‌های قابل فهم |
| Templates | مبتنی بر base template، partialهای کوچک و بدون query |
| Admin | امن، قابل جست‌وجو، دارای readonly fields برای داده حساس |

## 2-6- Celery

Celery برای وظایف پس‌زمینه در moduleهای `notifications.tasks`، `growth.tasks`، `orders.tasks`، `payments.tasks`، `loyalty.tasks`، `inventory.tasks` و `intelligence.tasks` استفاده می‌شود. توسعه task جدید باید با logging، retry و idempotency همراه باشد.

# 4- استاندارد توسعه

استاندارد توسعه در Crumbs بر خوانایی، تفکیک مسئولیت، تست‌پذیری و محافظت از flowهای حساس متمرکز است. تغییر کوچک هم اگر در checkout، payment، inventory یا order lifecycle باشد باید مانند تغییر پرریسک بررسی شود.

## 4-1- قوانین نام‌گذاری

| نوع | الگو |
| --- | --- |
| Model | اسم مفرد و دامنه‌ای مانند `Order` یا `ProductInventory` |
| Service class | نام دامنه + `Service` مانند `PaymentService` |
| Service function | فعل دقیق مانند `reserve_for_order` یا `finalize_checkout_stock` |
| Celery task | فعل + دامنه + پسوند `task` در صورت مناسب |
| Test file | `test_SUBJECT.py` |
| Template | نام دامنه و flow، با مسیر قابل فهم |
| Status value | مقدار ثابت کوتاه و پایدار مانند `awaiting_payment` |

## 4-2- ساختار فایل‌ها

| قانون | دلیل |
| --- | --- |
| فایل‌های طولانی باید بر اساس مسئولیت شکسته شوند | جلوگیری از سخت شدن review |
| serviceهای دامنه نباید در view پنهان شوند | امکان تست مستقل |
| importهای محلی فقط برای رفع circular dependency مجازند | کاهش coupling |
| helperهای مشترک باید در app مالک قرار بگیرند | جلوگیری از پراکندگی منطق |

## 4-3- Importها

- importهای استاندارد Python در ابتدای فایل قرار بگیرند.
- importهای Django پس از importهای استاندارد بیایند.
- importهای appهای داخلی پس از وابستگی‌های خارجی قرار بگیرند.
- import داخل function فقط وقتی قابل قبول است که circular dependency واقعی را حل کند.
- wildcard import استفاده نشود.

## 4-4- تقسیم مسئولیت

| اصل | توضیح |
| --- | --- |
| Single Responsibility | هر تابع، کلاس یا فایل باید یک دلیل اصلی برای تغییر داشته باشد. |
| Separation of Concerns | view، service، model، template و admin نباید مسئولیت یکدیگر را بگیرند. |
| Explicit Boundaries | boundaryهای transaction، permission و external provider باید واضح باشند. |
| Local Ownership | تغییر هر دامنه باید در app مالک آن دامنه شروع شود. |

# 5- توسعه Feature جدید

توسعه feature جدید باید از مسئله دامنه شروع شود، نه از پیاده‌سازی. ابتدا مشخص کنید feature به کدام app تعلق دارد، چه داده‌ای نیاز دارد، چه flowهایی را تغییر می‌دهد و چه تست‌هایی برای آن لازم است.

## 5-1- مراحل پیشنهادی

| مرحله | سؤال اصلی |
| --- | --- |
| انتخاب app | مالک دامنه feature کدام app است؟ |
| طراحی model | آیا داده جدید یا relation جدید لازم است؟ |
| Migration | آیا تغییر schema لازم است؟ |
| Service | آیا business rule یا mutation چندمدلی وجود دارد؟ |
| View | کاربر یا admin از کجا با feature تعامل می‌کند؟ |
| Template | آیا نمایش جدید، partial یا فرم لازم است؟ |
| Admin | آیا feature باید از پنل مدیریت قابل مشاهده یا کنترل باشد؟ |
| Tests | چه مسیرهای موفق، شکست و edge باید پوشش داده شود؟ |
| Documentation | آیا سند رسمی یا راهنمای مدیر باید به‌روزرسانی شود؟ |

## 5-2- انتخاب app

| سناریو | app مناسب |
| --- | --- |
| تغییر در سبد خرید | `cart` |
| تغییر در ساخت سفارش یا شماره سفارش | `orders` |
| تغییر در پرداخت، provider یا callback | `payments` |
| تغییر در موجودی یا reservation | `inventory` |
| تغییر در کوپن یا referral | `growth` |
| تغییر در امتیاز یا tier | `loyalty` |
| تغییر در پیامک یا template پیام | `notifications` |
| تغییر در داشبوردهای عملیاتی یا صفحات عمومی | `core` |
| تغییر در محصول یا دسته‌بندی | `products` |

## 5-3- معیار نیاز به Migration

Migration لازم است اگر:

- فیلد جدید به model اضافه شود.
- فیلد حذف یا rename شود.
- index، constraint یا relation تغییر کند.
- مقدار default پایدار برای داده موجود لازم باشد.
- مدل جدید اضافه شود.

Migration لازم نیست اگر:

- فقط منطق service تغییر کند.
- فقط template یا message تغییر کند.
- فقط query یا annotation اصلاح شود.
- فقط test یا documentation اضافه شود.

# 6- توسعه Model جدید

Model جدید باید فقط وقتی اضافه شود که داده پایدار جدید واقعاً لازم است. اگر داده فقط حاصل محاسبه است و نیاز به query یا history ندارد، ممکن است property، service یا snapshot موجود کافی باشد.

## 6-1- قوانین Model

| قانون | دلیل |
| --- | --- |
| نام model باید دامنه‌ای باشد | خوانایی در admin و migration |
| فیلدهای status باید محدود و مستند باشند | جلوگیری از مقدارهای نامعتبر |
| relationها باید جهت مالکیت را نشان دهند | کاهش ambiguity در query |
| مقدارهای پولی باید با Decimal سازگار باشند | جلوگیری از خطای عددی |
| فیلدهای زمانی باید timezone-aware باشند | سازگاری با Django و گزارش‌ها |

## 6-2- Meta، Index و Constraint

| مورد | چه زمانی استفاده شود |
| --- | --- |
| `ordering` | وقتی نمایش پیش‌فرض معنی دامنه‌ای دارد |
| `indexes` | برای queryهای پرتکرار، status، تاریخ یا foreign keyهای مهم |
| `constraints` | برای invariantهایی که باید در سطح database محافظت شوند |
| `unique_together` یا `UniqueConstraint` | برای جلوگیری از داده تکراری واقعی |
| `verbose_name` فارسی | برای خوانایی admin |

## 6-3- Validation و Relationships

Validation نزدیک به یک record می‌تواند در model یا form باشد. Validation وابسته به چند model یا وضعیت‌های خارجی باید در service قرار گیرد.

| نوع validation | محل مناسب |
| --- | --- |
| فرمت فیلد | form یا field validator |
| سازگاری دو فیلد یک model | model clean یا form clean |
| ظرفیت تولید و موجودی | service |
| وضعیت پرداخت و سفارش | service |
| مجوز کاربر | view یا admin action |

# 7- توسعه Service جدید

Service زمانی لازم است که تغییر شامل business rule، transaction، چند model، provider خارجی یا side effect باشد. View کافی است وقتی فقط نمایش داده، خواندن ساده یا redirect بدون mutation حساس انجام می‌شود.

## 7-1- چه زمانی Service لازم است

| وضعیت | Service لازم است؟ |
| --- | --- |
| تغییر وضعیت سفارش | بله |
| ثبت یا تأیید پرداخت | بله |
| رزرو یا مصرف موجودی | بله |
| ارسال پیامک وابسته به template | بله |
| اعمال coupon یا referral | بله |
| نمایش صفحه static | معمولاً خیر |
| فیلتر ساده لیست محصولات | معمولاً خیر |

## 7-2- الگوی پیشنهادی Service

```python
from django.db import transaction


class ExampleService:
    @staticmethod
    @transaction.atomic
    def execute(*, actor, target):
        # validate inputs
        # lock rows if needed
        # apply business rule
        # write changes
        # return explicit result
        return target
```

## 7-3- Transaction boundaries

| قانون | توضیح |
| --- | --- |
| transaction باید دور mutation حساس باشد | مخصوصاً پرداخت، سفارش و موجودی |
| lock باید نزدیک به query اصلی باشد | برای جلوگیری از race condition |
| کارهای خارجی طولانی داخل transaction قرار نگیرند | جلوگیری از نگه داشتن lock |
| نتیجه transaction باید قابل تست باشد | تست‌ها باید state نهایی را بررسی کنند |

## 7-4- Error handling

| نوع خطا | برخورد پیشنهادی |
| --- | --- |
| خطای validation کاربر | پیام قابل فهم در form یا view |
| خطای business rule | exception دامنه‌ای یا پیام کنترل‌شده |
| خطای provider خارجی | ثبت log امن و پاسخ قابل مدیریت |
| خطای idempotency | بازگرداندن نتیجه قبلی یا نادیده گرفتن تکرار امن |

# 8- توسعه View جدید

View باید ورودی و خروجی HTTP را مدیریت کند. اگر view بیش از حد درباره وضعیت سفارش، پرداخت، موجودی یا چند model تصمیم می‌گیرد، بخشی از منطق باید به service منتقل شود.

## 8-1- CBV vs FBV

| گزینه | کاربرد مناسب |
| --- | --- |
| FBV | flowهای خاص، checkout، actionهای عملیاتی و منطق کنترل‌شده |
| CBV | CRUD ساده، نمایش‌های قابل تعمیم یا viewهای استاندارد |

## 8-2- Validation، Messages و Redirects

| بخش | استاندارد |
| --- | --- |
| Validation | با form یا service انجام شود، نه با شرط‌های پراکنده |
| Messages | فارسی، کوتاه و مناسب کاربر |
| Redirect | پس از POST موفق برای جلوگیری از ارسال دوباره |
| Permission | پیش از mutation بررسی شود |
| Access control | سفارش و داده شخصی فقط برای کاربر مجاز نمایش داده شود |

## 8-3- Permissionها

| سناریو | کنترل |
| --- | --- |
| صفحه عمومی | نیازی به login ندارد |
| حساب کاربری | login required |
| مشاهده سفارش | مالک سفارش یا دسترسی checkout session |
| admin route | staff یا permission مناسب |
| action عملیاتی | استفاده از service و بررسی وضعیت |

# 9- توسعه Template

Templateها باید برای نمایش داده استفاده شوند. منطق دامنه، query و mutation نباید داخل template قرار گیرد. ساختار فعلی از templateهای عمومی، account، shop، order و admin استفاده می‌کند.

## 9-1- ساختار Templates

| مسیر | کاربرد |
| --- | --- |
| `templates/base.html` | قالب پایه عمومی |
| `templates/pages/` | صفحات عمومی |
| `templates/shop/` | فروشگاه و محصول |
| `templates/accounts/` | حساب کاربری |
| `templates/orders/` | سفارش، رسید و تایم‌لاین |
| `templates/admin/` | پنل مدیریت و صفحات عملیاتی |

## 9-2- Reuse و Partials

| قانون | دلیل |
| --- | --- |
| بخش‌های تکراری به partial منتقل شوند | جلوگیری از duplication |
| نام partial باید دامنه را نشان دهد | پیدا کردن آسان‌تر در review |
| template نباید query جدید بسازد | جلوگیری از N+1 و پنهان شدن منطق |
| context باید در view آماده شود | قابل تست بودن view |

## 9-3- CSS/JS separation

CSS و JavaScript عمومی در `static` نگهداری می‌شوند. اگر رفتار جدید فقط برای یک template است، ابتدا بررسی شود که آیا رفتار عمومی‌تر یا reusable وجود دارد یا نه. inline script فقط در صورت ضرورت و با دلیل قابل قبول است.

# 10- توسعه Admin

Admin در Crumbs ابزار عملیاتی مهمی است. تغییر admin باید هم برای مدیر سایت قابل فهم باشد و هم از تغییرهای خطرناک جلوگیری کند.

## 10-1- ModelAdmin

| بخش | توصیه |
| --- | --- |
| `list_display` | فیلدهای عملیاتی و قابل تشخیص |
| `list_filter` | status، تاریخ، provider و دسته‌بندی‌های مهم |
| `search_fields` | شماره سفارش، ایمیل، موبایل، نام محصول یا کد |
| `readonly_fields` | فیلدهای مالی، provider response، شماره‌ها و audit data |
| `actions` | فقط actionهای امن و مبتنی بر service |

## 10-2- Performance

| مشکل | راهکار |
| --- | --- |
| Query زیاد در لیست admin | استفاده از `select_related` یا `prefetch_related` |
| محاسبه سنگین در column | انتقال به annotation یا service سبک |
| نمایش داده حساس | readonly و mask کردن مقدار |
| actionهای bulk خطرناک | حذف یا محدودسازی |

## 10-3- حذف و تغییر مستقیم

برای سفارش، پرداخت، رزرو موجودی و درخواست‌های حساس نباید حذف یا تغییر مستقیم بدون service انجام شود. اگر action جدید لازم است، ابتدا service دامنه‌ای نوشته شود و admin فقط آن service را صدا بزند.

# 11- توسعه Celery Task

Celery برای کارهایی استفاده می‌شود که زمان‌بر، دوره‌ای، وابسته به سرویس خارجی یا غیرضروری برای پاسخ فوری HTTP هستند.

## 11-1- چه زمانی Task بنویسیم

| سناریو | Task مناسب است؟ |
| --- | --- |
| ارسال پیامک | بله |
| cleanup پرداخت stale | بله |
| refresh segmentهای مشتری | بله |
| snapshot روزانه | بله |
| محاسبه کوتاه داخل view | خیر |
| mutation حساس که باید فوری نتیجه بدهد | معمولاً خیر |

## 11-2- Naming، Retry و Logging

| موضوع | استاندارد |
| --- | --- |
| Naming | نام task باید فعل و دامنه را نشان دهد |
| Retry | برای خطای موقت خارجی استفاده شود |
| Logging | شروع، پایان و خطا با context امن ثبت شود |
| Idempotency | اجرای تکراری نباید داده را خراب کند |
| Queue | task باید در صف مناسب اجرا شود |

## 11-3- Idempotency

Taskهایی که پرداخت، پیامک، امتیاز یا snapshot را تغییر می‌دهند باید برای اجرای دوباره امن باشند. وجود log، status، unique constraint یا بررسی state قبلی می‌تواند از اثر تکراری جلوگیری کند.

# 12- توسعه API یا Integration

Crumbs در پرداخت و پیامک از الگوی provider استفاده می‌کند. توسعه integration جدید باید پشت interface مشخص انجام شود تا view و serviceهای دامنه به جزئیات سرویس خارجی وابسته نشوند.

## 12-1- Provider Pattern

| بخش | نمونه فعلی |
| --- | --- |
| Payment provider base | `payments.providers.base.PaymentProvider` |
| Zarinpal provider | `payments.providers.zarinpal.ZarinpalPaymentProvider` |
| Stripe provider | `payments.providers.stripe.StripePaymentProvider` |
| SMS provider | providerهای موجود در `notifications.services` |

## 12-2- External Services

| قانون | دلیل |
| --- | --- |
| Timeout و خطا باید کنترل شود | جلوگیری از hang شدن request یا task |
| Secret نباید log شود | امنیت production |
| Response خام باید با احتیاط ذخیره شود | جلوگیری از نگهداری داده حساس |
| Callback باید idempotent باشد | جلوگیری از ثبت چندباره پرداخت |
| تست باید mock provider داشته باشد | جلوگیری از وابستگی تست به سرویس خارجی |

## 12-3- Payment Providers

تغییر در provider پرداخت باید با دقت انجام شود. `PaymentService` مسئول ساخت، reuse، وضعیت و callback پرداخت است و تغییر provider نباید منطق سفارش را دور بزند.

## 12-4- SMS Providers

ارسال پیامک از طریق service و task انجام می‌شود. توسعه provider جدید باید با template، log، retry و quiet hours/rate limits موجود سازگار باشد.

# 13- توسعه تست‌ها

تست‌ها در Crumbs چند سطح دارند و باید با ریسک تغییر متناسب باشند. تغییر ساده در template ممکن است به تست UI نیاز داشته باشد؛ تغییر در پرداخت یا موجودی حتماً به تست service، integration و edge نیاز دارد.

## 13-1- لایه‌های تست

| لایه | مسیر | کاربرد |
| --- | --- | --- |
| Unit Tests | `tests/unit/` | تست service، form، admin، UI markup و helperها |
| Integration Tests | `tests/integration/` | تست flowهای checkout، پرداخت، SMS، coupon و referral |
| Edge Case Tests | `tests/edge_cases/` | سناریوهای شکست و وضعیت‌های مرزی |
| Concurrency Tests | `tests/concurrency/` | race condition و رفتار `select_for_update` |
| Celery Tests | `tests/celery/` | reliability و logging taskها |
| Load Guide | `tests/load/README.md` | راهنمای شبیه‌سازی load؛ کد خودکار load test نیست |

## 13-2- Naming

| نوع تست | الگو |
| --- | --- |
| تست service | `test_SERVICE_BEHAVIOR` |
| تست flow | `test_flow_DOMAIN` |
| تست edge | `test_FAILURE_SCENARIO` |
| تست admin | `test_MODEL_admin_BEHAVIOR` |
| تست task | `test_TASK_EXPECTED_RESULT` |

## 13-3- Factories و داده تست

فایل `tests/factories.py` helperهای سبک برای ساخت user، product، cart، order، coupon، referral و SMS template دارد. تست جدید باید تا جای ممکن از همین helperها استفاده کند تا داده تست در فایل‌های مختلف تکرار نشود.

## 13-4- Assertions

| نوع assertion | نمونه |
| --- | --- |
| وضعیت مدل | status، payment status، reservation status |
| اثر جانبی | ایجاد Payment، SMSLog، StockReservation یا transaction امتیاز |
| پاسخ HTTP | status code، redirect، message |
| امنیت | نبود داده غیرمجاز در response |
| idempotency | اجرای دوباره callback یا task بدون اثر مخرب |

# 14- Logging و Debugging

Logging برای production و توسعه اهمیت دارد. لاگ باید برای تشخیص مشکل کافی باشد، اما نباید secret، token، اطلاعات پرداخت یا داده حساس کاربر را افشا کند.

## 14-1- Logging

| مورد | توصیه |
| --- | --- |
| logger دامنه‌ای | برای payment، order و task از logger مشخص استفاده شود |
| context | شناسه سفارش، payment id یا provider کافی است |
| داده حساس | رمز، token، شماره کامل کارت یا secret نباید log شود |
| سطح log | خطای قابل اقدام با error، رخداد عملیاتی با info |

## 14-2- Observability

جزئیات Observability در `docs/OBSERVABILITY.md` مستند شده است. توسعه‌دهنده فقط باید مطمئن شود تغییر جدید لاگ امن و قابل پیگیری دارد.

## 14-3- Health Endpoints و Readiness Endpoints

| Endpoint | کاربرد توسعه‌ای |
| --- | --- |
| `/health/` | بررسی زنده بودن سرویس |
| `/ready/` | بررسی Database، Redis، Broker و Migrationها |
| `/health/full/` | diagnostics اختیاری در شرایط مشخص |

## 14-4- Sentry

Sentry اختیاری است و با `SENTRY_DSN` فعال می‌شود. خطاهای جدید باید به شکلی مدیریت شوند که در صورت فعال بودن Sentry، context کافی و امن برای تشخیص مشکل وجود داشته باشد.

- دلیل تغییر
- فایل‌ها یا دامنه‌های درگیر
- ریسک‌های احتمالی
- تست‌های اجراشده
- اثر روی مستندات، اگر وجود دارد

## 18-4- Merge و Versioning

Merge باید پس از review و عبور تست‌ها انجام شود. اگر تغییر روی رفتار production اثر دارد، نسخه مستندشده و اسناد مرتبط باید با وضعیت واقعی هماهنگ بمانند.

# 19- توسعه نسخه‌های آینده

توسعه نسخه‌های آینده باید معماری فعلی را حفظ کند، مگر اینکه دلیل فنی و محصولی کافی برای تغییر معماری وجود داشته باشد. هدف، توسعه تدریجی بدون شکستن flowهای سفارش، پرداخت و موجودی است.

## 19-1- اصول حفظ معماری

| اصل | توضیح |
| --- | --- |
| حفظ مرز appها | هر دامنه در app مالک خود توسعه یابد. |
| حفظ Service Layer | mutationهای حساس در service باقی بمانند. |
| حفظ تست‌های regression | flowهای اصلی بدون تست تغییر نکنند. |
| حفظ مستندات | تغییر behavior باید در سند مرتبط ثبت شود. |

## 19-2- Backward compatibility

Backward compatibility برای داده‌های موجود، migrationها، مسیرهای عمومی، payment callbackها و statusهای پایدار اهمیت دارد. تغییر در این بخش‌ها باید با migration strategy و تست کافی همراه باشد.

## 19-3- Migration strategy

| نوع تغییر | راهبرد |
| --- | --- |
| افزودن فیلد nullable | migration ساده و سپس پر کردن تدریجی |
| افزودن فیلد required | default یا data migration کنترل‌شده |
| rename فیلد | بررسی داده، migration و تست |
| حذف فیلد | ابتدا حذف استفاده از کد، سپس migration حذف |
| تغییر constraint | تست داده موجود و سناریوهای شکست |

## 19-4- Refactoring

Refactor باید رفتار را ثابت نگه دارد. پیش از refactor، تست‌های موجود اجرا شوند و اگر پوشش کافی نیست، ابتدا تست محافظ اضافه شود.

# 20- پرسش‌های متداول

## 20-1- برای feature جدید از کدام app شروع کنم؟

از دامنه اصلی feature شروع کنید. اگر feature درباره پرداخت است از `payments`، اگر درباره سفارش است از `orders`، و اگر درباره موجودی است از `inventory` شروع کنید.

## 20-2- چه زمانی service جدید بنویسم؟

وقتی تغییر شامل business rule، چند model، transaction، provider خارجی یا side effect باشد، service لازم است.

## 20-3- آیا می‌توانم منطق را در view نگه دارم؟

برای نمایش ساده یا redirect بله؛ برای تغییر وضعیت سفارش، پرداخت، موجودی یا flowهای حساس خیر.

## 20-4- برای تغییر status سفارش چه کنم؟

مسیر رسمی باید از `OrderService` و state machine موجود عبور کند. تغییر مستقیم status توصیه نمی‌شود.

## 20-5- برای پرداخت provider جدید چگونه شروع کنم؟

ابتدا interface موجود در providerهای `payments` را بررسی کنید و provider جدید را پشت همان pattern اضافه کنید. سپس `PaymentService` و تست‌های provider را به‌روزرسانی کنید.

## 20-6- آیا برای هر تغییر باید migration بسازم؟

خیر. فقط تغییر schema، index، constraint یا داده پایدار به migration نیاز دارد.

## 20-7- تست کدام بخش‌ها ضروری‌تر است؟

checkout، payment، inventory reservation، order lifecycle، admin actionهای حساس و taskهای پس‌زمینه بیشترین اولویت را دارند.

## 20-8- آیا task جدید باید retry داشته باشد؟

اگر task به سرویس خارجی یا خطای موقت وابسته است، retry لازم است. اگر task mutation حساس دارد، idempotency هم باید طراحی شود.

## 20-9- کجا باید مستندات را به‌روزرسانی کنم؟

اگر رفتار کاربر، مدیر سایت، معماری، استقرار یا توسعه تغییر کند، سند مربوط به همان حوزه باید به‌روزرسانی شود.

## 20-10- قبل از ارسال PR چه دستورهایی اجرا کنم؟

حداقل `python manage.py check` و تست‌های مرتبط با تغییر را اجرا کنید. برای تغییرهای گسترده، اجرای `pytest -q` توصیه می‌شود.

# 21- جمع‌بندی

توسعه Crumbs باید با احترام به معماری app-based، Service Layer، transactionهای صریح، تست‌پذیری و مرزبندی دامنه انجام شود. بخش‌های checkout، payment، inventory و order lifecycle حساس‌ترین نقاط پروژه هستند و هر تغییر در آن‌ها باید با تست و review دقیق همراه باشد.
