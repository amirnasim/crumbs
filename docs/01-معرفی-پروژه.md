# ۱- مقدمه

Crumbs یک سامانه تحت وب برای سفارش‌گیری، پرداخت، کنترل موجودی، مدیریت عملیات کافه و بیکری و پشتیبانی از فرآیندهای مدیریتی است. این سامانه با Django پیاده‌سازی شده و ساختار آن بر اساس چند اپلیکیشن دامنه‌محور در پوشه `apps` شکل گرفته است.

Crumbs برای کسب‌وکاری طراحی شده که فروش محصولات کافه و بیکری را از مرحله مشاهده محصول تا ثبت سفارش، پرداخت، آماده‌سازی، تحویل از کانتر، گزارش‌گیری و عملیات پس از فروش در یک بستر واحد مدیریت می‌کند. تمرکز فعلی سیستم بر سفارش‌گیری آنلاین و تحویل حضوری از کانتر است. برخی قابلیت‌های ارسال قدیمی در مدل‌ها و سرویس‌ها نگهداری شده‌اند، اما `checkout` فعال فعلی بر `pickup` در کافه بنا شده است.

این پروژه برای حل چند مسئله اصلی ایجاد شده است:

- پراکندگی داده‌های محصول، سفارش، پرداخت، موجودی و مشتری
- نبود کنترل دقیق روی موجودی قابل فروش و ظرفیت تولید روزانه
- نیاز به ثبت سفارش سریع و قابل پیگیری برای محیط کافه
- نیاز به تفکیک عملیات صندوق، آشپزخانه، کانتر و مدیریت
- نیاز به آماده‌سازی پروژه برای استقرار واقعی روی VPS با Docker، Nginx، Gunicorn، PostgreSQL، Redis و Celery
- نیاز به گزارش‌های عملیاتی و داده‌های رشد برای تصمیم‌گیری مدیریتی

کسب‌وکارهای هدف Crumbs شامل کافه‌ها، بیکری‌ها، شیرینی‌پزی‌های کوچک و متوسط، فروشگاه‌های خوراکی دست‌ساز و مجموعه‌هایی هستند که سفارش آنلاین، پرداخت آنلاین یا حضوری، تولید محدود روزانه و تحویل از کانتر برای آن‌ها اهمیت عملیاتی دارد.

کاربران هدف سیستم شامل مشتری مهمان، مشتری ثبت‌نام‌شده، صندوق‌دار، تیم آشپزخانه، مسئول کانتر، مدیر فروشگاه، مدیر سیستم و توسعه‌دهنده نگهدارنده پروژه هستند.

اهداف عمومی پروژه عبارت‌اند از:

- ارائه تجربه ساده و فارسی برای مشتری
- ثبت سفارش با حداقل اصطکاک و داده‌های ضروری
- جلوگیری از فروش بیش از موجودی یا ظرفیت تولید
- ثبت جریان پرداخت آنلاین و حضوری
- ایجاد دید عملیاتی برای کارکنان فروشگاه
- نگهداری‌پذیری کد و آماده‌سازی برای توسعه بلندمدت
- آمادگی استقرار تولیدی با مستندات، Health check، backup و Observability

# ۲- اهداف پروژه

## ۲-۱- اهداف کسب‌وکار

| هدف | توضیح |
| --- | --- |
| یکپارچه‌سازی فروش | محصولات، سبد خرید، سفارش، پرداخت و مشتری در یک سیستم واحد نگهداری می‌شوند. |
| کاهش خطای فروش | موجودی و ظرفیت قبل از ثبت سفارش بررسی می‌شود تا از فروش بیش از توان تولید جلوگیری شود. |
| پشتیبانی از پرداخت‌های متناسب با بازار ایران | پرداخت آنلاین از طریق Zarinpal و پرداخت حضوری در `checkout` پشتیبانی شده است. |
| افزایش قابلیت پیگیری سفارش | سفارش‌ها دارای شماره سفارش، شماره روزانه، وضعیت پرداخت، وضعیت عملیات و رسید هستند. |
| مدیریت تجربه مشتری | پیام‌ها، خطاها، تایم‌لاین سفارش و صفحات کاربری به زبان فارسی ارائه می‌شوند. |

Crumbs فقط یک فروشگاه آنلاین ساده نیست. پروژه برای اتصال فروش دیجیتال به عملیات واقعی کافه طراحی شده است؛ یعنی سفارش ثبت‌شده باید برای صندوق، آشپزخانه، کانتر و مدیر قابل فهم و پیگیری باشد.

# ۳- دامنه پروژه

## ۳-۱- محدوده سمت مشتری

سمت مشتری شامل صفحات عمومی و جریان خرید است. کاربر می‌تواند بدون ورود به سیستم، محصولات را مشاهده کند، محصول را به سبد اضافه کند و `checkout` انجام دهد. اگر کاربر وارد حساب کاربری شده باشد، سفارش به حساب او متصل می‌شود و در بخش سفارش‌های حساب کاربری قابل مشاهده است.

| بخش | پوشش فعلی |
| --- | --- |
| صفحه اصلی | نمایش محصولات ویژه و پیشنهادهای مبتنی بر سرویس توصیه‌گر |
| فروشگاه | لیست محصولات فعال و فیلتر بر اساس دسته‌بندی |
| جزئیات محصول | نمایش اطلاعات محصول، قیمت، توضیحات، تصویر و محصولات مرتبط |
| سبد خرید | افزودن، حذف، تغییر تعداد و نمایش جمع اقلام |
| `checkout` | دریافت نام، شماره تماس، ایمیل اختیاری، یادداشت یا شماره میز و روش پرداخت |
| پرداخت | پرداخت آنلاین و پرداخت حضوری |
| تأیید سفارش | نمایش سفارش ثبت‌شده و وضعیت آن |
| رسید سفارش | نمایش اطلاعات قابل پیگیری سفارش |
| حساب کاربری | ورود، ثبت‌نام، پروفایل، آدرس‌ها و سفارش‌های کاربر |
| علاقه‌مندی‌ها | ذخیره محصول برای کاربران واردشده |
| فرم همکاری | ثبت درخواست همکاری و رزومه PDF |

## ۳-۲- محدوده سمت مدیریت

سمت مدیریت بر پایه پنل مدیریت Django و چند صفحه عملیاتی سفارشی ساخته شده است. دسترسی به صفحات عملیاتی با `staff_member_required` کنترل می‌شود.

| بخش | پوشش فعلی |
| --- | --- |
| مدیریت محصولات | دسته‌بندی، محصول، تصویر، قیمت، وضعیت موجودی و featured |
| مدیریت سفارش | وضعیت سفارش، وضعیت پرداخت، شماره سفارش، شماره روزانه و اقلام |
| مدیریت پرداخت | Payment، `PaymentEvent` و وضعیت‌های پرداخت |
| مدیریت موجودی | موجودی محصول، رزروها، ظرفیت تولید روزانه |
| عملیات | داشبورد عملیات، `task` center، صف آشپزخانه، صفحه `pickup`، جست‌وجوی سفارش، خلاصه شیفت |
| بازاریابی و رشد | کوپن، پروموشن، معرف، سبد رهاشده و رویدادهای رشد |
| وفاداری | حساب وفاداری، امتیاز، سطح مشتری و تراکنش امتیاز |
| پیامک و اطلاع‌رسانی | قالب پیامک، لاگ پیامک و `provider`ها |
| استخدام | مدیریت درخواست‌های همکاری |
| Observability داخلی | لاگ `task`های پس‌زمینه و خطاهای operational |

## ۳-۳- محدوده عملیاتی

Crumbs جریان کار کافه را از لحظه ثبت سفارش تا تحویل پوشش می‌دهد:

- سفارش آنلاین پس از پرداخت موفق، به وضعیت پرداخت‌شده و سپس تأییدشده توسط فروشگاه منتقل می‌شود.
- سفارش پرداخت حضوری ابتدا در وضعیت انتظار پرداخت صندوق قرار می‌گیرد.
- پس از ثبت دریافت وجه، سفارش حضوری وارد وضعیت آماده‌سازی می‌شود.
- تیم آشپزخانه سفارش را از صف انتظار به آماده‌سازی و سپس آماده تحویل منتقل می‌کند.
- مسئول کانتر سفارش آماده را تحویل‌شده ثبت می‌کند.
- موجودی و ظرفیت تولید در طول مسیر مدیریت می‌شوند.

## ۳-۵- موارد خارج از دامنه فعلی

موارد زیر در دامنه فعال فعلی پروژه نیستند یا فقط زیرساخت/مدل اولیه آن‌ها وجود دارد:

| مورد | وضعیت |
| --- | --- |
| ارسال فعال با پیک در `checkout` عمومی | مدل‌ها و سرویس‌های `legacy` وجود دارند، اما `checkout` فعلی بر تحویل از کانتر است. |
| مدیریت ناوگان ارسال | پیاده‌سازی نشده است. |
| اتصال مستقیم به دستگاه `POS` فیزیکی | پیاده‌سازی نشده است. پرداخت حضوری در سیستم ثبت می‌شود، اما سخت‌افزار صندوق خارج از پروژه است. |
| حسابداری مالی کامل | گزارش فروش و پرداخت وجود دارد، اما حسابداری رسمی، سند حسابداری و مالیات کامل خارج از دامنه است. |
| مدیریت چند شعبه | در ساختار فعلی مدل شعبه یا تفکیک شعبه پیاده‌سازی نشده است. |
| مدیریت تأمین‌کننده و خرید مواد اولیه | موجودی محصول و ظرفیت تولید وجود دارد، اما procurement مواد اولیه پیاده‌سازی نشده است. |
| اپلیکیشن موبایل native | پروژه وب است و اپ موبایل native ندارد. |
| پنل `BI` خارجی | snapshotها و مدل‌های تحلیلی وجود دارند، اما اتصال به `BI` خارجی جزو دامنه فعلی نیست. |
| `ATS` کامل استخدام | فرم درخواست همکاری و مدیریت درخواست وجود دارد، اما سیستم کامل استخدام سازمانی پیاده‌سازی نشده است. |

| Developer | دسترسی کد و محیط | توسعه، تست، migration، `deploy`، بررسی log و رفع اشکال | نباید داده تولیدی یا secrets را در مخزن commit کند. |

## ۴-۲- Guest

Guest کاربری است که وارد حساب نشده اما `session` دارد. سیستم در صورت نبود `session_key` یک `session` ایجاد می‌کند و سبد خرید را با `session` نگهداری می‌کند. Guest می‌تواند محصول را به سبد اضافه کند و `checkout` انجام دهد. در `checkout` اگر ایمیل وارد نشود، سیستم یک ایمیل داخلی با الگوی `guest+phone@crumbs.local` می‌سازد تا مدل سفارش مقدار ایمیل معتبر داشته باشد.

مسئولیت‌های سیستم برای Guest:

- نگهداری سبد با `session`
- نمایش پیام‌های فارسی در خطاهای سبد و `checkout`
- کنترل دسترسی به سفارش ثبت‌شده از طریق access موقت `checkout`
- جلوگیری از مشاهده رسید یا سفارش بدون دسترسی معتبر

## ۴-۳- Registered Customer

مشتری ثبت‌نام‌شده علاوه بر امکانات Guest، به پروفایل، آدرس‌ها، سفارش‌ها و `wishlist` دسترسی دارد. اگر کاربر پس از داشتن سبد `session` وارد شود، سرویس `cart` امکان merge سبد `session` در سبد کاربر را دارد.

داده‌های مرتبط:

- `CustomerProfile`
- `Address`
- `Cart`
- `Order`
- `WishlistItem`
- `LoyaltyAccount`
- `ReferralCode`

## ۴-۴- Cashier

Cashier با سفارش‌های پرداخت حضوری سروکار دارد. سفارش‌های پرداخت حضوری در `checkout` با وضعیت `AWAITING_PAYMENT` و payment `pending` ایجاد می‌شوند. صندوق‌دار پس از دریافت وجه، پرداخت را در سیستم ثبت می‌کند. پس از ثبت پرداخت حضوری، سفارش به وضعیت آماده‌سازی منتقل می‌شود و رزرو موجودی تأیید می‌گردد.

عملیات مهم:

- مشاهده سفارش‌های در انتظار پرداخت صندوق
- ثبت دریافت وجه نقد یا کارت در کانتر
- استفاده از جست‌وجوی سفارش با شماره سفارش، شماره روزانه، تلفن، نام یا یادداشت

## ۴-۵- Kitchen

کاربر Kitchen مسئول آماده‌سازی سفارش است. صفحه آشپزخانه فقط سفارش‌هایی را نشان می‌دهد که از نظر پرداخت معتبر هستند و در یکی از وضعیت‌های قابل آماده‌سازی قرار دارند.

وضعیت‌های قابل مشاهده در صف آشپزخانه:

- `PAID`
- `CONFIRMED_BY_SHOP`
- `PREPARING`
- `PACKAGED`

اقدام‌ها:

- شروع آماده‌سازی
- علامت‌گذاری سفارش به‌عنوان آماده تحویل
- تکمیل سفارش در مسیر مشترک `pickup`

## ۴-۶- Counter

Counter سفارش‌های آماده تحویل از کانتر را می‌بیند. این سفارش‌ها باید وضعیت `PACKAGED` و پرداخت معتبر داشته باشند. با ثبت تحویل، سیستم سفارش را از مسیر `pickup` completion عبور می‌دهد و در نهایت به `DELIVERED` منتقل می‌کند.

## ۴-۷- Manager

Manager دید عملیاتی و مدیریتی دارد. مهم‌ترین بخش‌های قابل استفاده برای مدیر:

- عملیات روزانه و `task` center
- خلاصه شیفت
- سفارش‌های جدید و در آماده‌سازی
- موجودی کم و محصولات فاقد موجودی
- پرداخت‌های ناموفق یا stale
- سفارش‌های در انتظار پرداخت حضوری
- داده‌های محصول، رشد و مشتری

## ۴-۸- Administrator

Administrator مسئول مدیریت سطح بالای سیستم است. این نقش در پنل مدیریت Django می‌تواند داده‌های اصلی، کاربران، دسترسی‌ها و مدل‌های مدیریتی را کنترل کند. دسترسی `superuser` باید محدود، مستندسازی‌شده و محافظت‌شده باشد.

## ۴-۹- Developer

Developer مسئول نگهداری فنی است. وظایف او شامل توسعه feature، نوشتن تست، اجرای migration، بررسی health/readiness endpoints، بررسی لاگ، انجام `deploy`، backup و رفع اشکال است. Developer باید از مستندات `docs` و اسکریپت‌های `deploy` استفاده کند.

# ۵- معرفی بخش‌های اصلی سیستم

## ۵-۱- Products

زیرسیستم محصولات مسئول تعریف کاتالوگ فروشگاه است. هر محصول به یک دسته‌بندی وصل است، قیمت دارد، توضیح و مواد اولیه دارد، تصویر می‌تواند داشته باشد و با `availability_status` کنترل می‌شود.

| جزء | توضیح |
| --- | --- |
| مدل‌های اصلی | `Category`، `Product` |
| وضعیت محصول | `available`، `out_of_stock`، `coming_soon` |
| مسیر عمومی | `/shop/` و مسیرهای دسته‌بندی/جزئیات |
| ارتباطات | محصول به `cart` item، order item، `inventory`، `intelligence` و `wishlist` متصل است. |

هدف این بخش ارائه منوی قابل مدیریت و قابل نمایش برای مشتری است.

## ۵-۲- Shopping Cart

سبد خرید هم برای کاربر واردشده و هم برای Guest پشتیبانی می‌شود. هر سبد یا به user وصل است یا به `session`. هر محصول در هر سبد فقط یک `CartItem` دارد و تعداد آن مثبت است.

رفتارهای مهم:

- ایجاد یا دریافت سبد با user یا `session`
- افزودن محصول فقط در صورت `available` بودن
- کنترل تعداد معتبر
- بررسی موجودی قبل از تغییر سبد
- رزرو موجودی برای سبد
- آزادسازی رزرو هنگام حذف یا پاک‌سازی سبد
- قفل کردن تغییرات سبد هنگام `checkout` فعال

## ۵-۳- Checkout

`checkout` فعلی روی تحویل از کانتر طراحی شده است. فرم `checkout` فیلدهای اصلی نام، شماره تماس، ایمیل اختیاری، یادداشت/شماره میز و روش پرداخت را دریافت می‌کند.

روش‌های پرداخت عمومی فعلی:

| مقدار داخلی | نمایش به مشتری |
| --- | --- |
| `online` | پرداخت آنلاین |
| `cash` | پرداخت حضوری |

در `backend` مقدار `counter_card` نیز برای داده‌های قبلی و عملیات داخلی حفظ شده است، اما انتخاب عمومی `checkout` فعلی دو گزینه دارد.

## ۵-۴- Orders

زیرسیستم سفارش، نتیجه `checkout` را به یک موجودیت قابل پیگیری تبدیل می‌کند. سفارش شامل شماره سفارش، شماره روزانه، وضعیت سفارش، وضعیت پرداخت، اطلاعات مشتری، اقلام، جمع کل، تخفیف، کوپن، کد معرف و تاریخ fulfillment است.

وضعیت‌های اصلی سفارش:

- `pending_payment`
- `awaiting_payment`
- `paid`
- `confirmed_by_shop`
- `preparing`
- `packaged`
- `out_for_delivery`
- `delivered`
- `cancelled`
- `refunded`

وضعیت‌های پرداخت در مدل `Order.PaymentStatus`:

| مقدار | کاربرد |
| --- | --- |
| `pending_payment` | در انتظار پرداخت |
| `paid` | پرداخت نهایی‌شده |
| `cod_pending` | وضعیت `legacy` پرداخت در محل |
| `cod_confirmed` | وضعیت `legacy` تأیید پرداخت در محل |
| `cash_received` | دریافت وجه نقد/حضوری در جریان‌های `legacy` یا تکمیل دریافت وجه |
| `failed` | پرداخت ناموفق |
| `refund_requested` | درخواست استرداد |
| `refund_processed` | استرداد پردازش‌شده |

روش‌های پرداخت در مدل `Order.PaymentMethod`:

| مقدار | وضعیت استفاده |
| --- | --- |
| `online` | گزینه عمومی `checkout` برای پرداخت آنلاین |
| `cash` | گزینه عمومی `checkout` برای پرداخت حضوری |
| `counter_card` | مقدار `backend` برای پرداخت کارت در کانتر؛ در فرم عمومی `checkout` نمایش داده نمی‌شود |
| `cod` | مقدار `legacy` برای پرداخت در محل |

## ۵-۵- Payments

پرداخت‌ها در مدل `Payment` ثبت می‌شوند و به سفارش وصل هستند. سیستم از `provider`های مختلف پشتیبانی می‌کند.

`Provider`های موجود:

- `zarinpal`
- `stripe`
- `cod`
- `cash`
- `counter_card`

پرداخت آنلاین اصلی برای بازار ایران Zarinpal است. Stripe به صورت اختیاری و وابسته به تنظیمات وجود دارد.

وضعیت‌های مدل `Payment.Status`:

| مقدار | کاربرد |
| --- | --- |
| `pending` | پرداخت ایجادشده اما هنوز وارد پردازش نهایی نشده است |
| `processing` | پرداخت آنلاین دارای `checkout` `session` فعال است |
| `succeeded` | پرداخت موفق |
| `failed` | پرداخت ناموفق |
| `cancelled` | پرداخت لغوشده |
| `refunded` | پرداخت مستردشده |

## ۵-۶- Inventory

Inventory موجودی قابل فروش و ظرفیت تولید روزانه را کنترل می‌کند. این بخش از فروش بیش از موجودی یا بیش از ظرفیت تولید جلوگیری می‌کند.

اجزای اصلی:

- `ProductInventory`
- `DailyProductionCapacity`
- `StockReservation`

رزرو موجودی هم برای سبد خرید و هم برای سفارش انجام می‌شود. رزروهای سبد زمان‌دار هستند و `task` دوره‌ای برای منقضی کردن آن‌ها وجود دارد.

## ۵-۷- Delivery

در وضعیت فعلی کد، اپلیکیشن `delivery` بخشی از fulfillment قدیمی و وضعیت سفارش را پوشش می‌دهد. label داخلی این اپ در Django برابر `fulfillment` است. `checkout` فعال از `PICKUP` استفاده می‌کند و هزینه ارسال صفر است. مدل `DeliveryZone` و سرویس محاسبه هزینه برای سناریوهای `legacy` ارسال حفظ شده‌اند.

کارکرد مهم فعلی `delivery`:

- state machine وضعیت سفارش
- لاگ تغییر وضعیت سفارش
- orchestration پرداخت آنلاین و `pickup` `checkout`

## ۵-۸- Loyalty

زیرسیستم `loyalty` حساب امتیاز مشتری را مدیریت می‌کند. امتیاز بر اساس مبلغ سفارش پرداخت‌شده محاسبه می‌شود و سطح مشتری با thresholdهای تنظیمات تعیین می‌گردد.

سطح‌ها:

- `normal`
- `silver`
- `gold`

قانون فعلی امتیازدهی از تنظیم `LOYALTY_POINTS_PER_1000_TOMAN` استفاده می‌کند.

## ۵-۹- Growth

Growth برای کمپین‌ها، کوپن‌ها، referral، سبد رهاشده، رویدادهای رشد و تحلیل درآمد استفاده می‌شود.

اجزای مهم:

- `Coupon`
- `CouponRedemption`
- `ReferralCode`
- `Referral`
- `PromotionRule`
- `GrowthEvent`
- `AbandonedCartTracker`
- `CustomerSegment`
- `CustomerCLVProfile`
- `DailyRevenueSnapshot`
- `FunnelAnalyticsSnapshot`

## ۵-۱۰- Intelligence

Intelligence لایه داده‌ای برای پیشنهاد فروش، تحلیل محصول، پیش‌بینی تقاضا و توصیه پخت است. این بخش مستقل از `checkout` اصلی کار می‌کند اما در صفحه اصلی، جزئیات محصول، سبد و `checkout` برای پیشنهاد محصول استفاده می‌شود.

اجزای مهم:

- `ProductIntelligenceMeta`
- `ProductCoPurchase`
- `ProductDailyStats`
- `ProductDemandForecast`
- `ProductBakeRecommendation`
- `CustomerIntelligenceProfile`
- `IntelligenceSnapshot`
- `UpsellImpression`

## ۵-۱۱- Careers

Careers فرم درخواست همکاری را پوشش می‌دهد. متقاضی می‌تواند اطلاعات تماس، سن، منطقه زندگی، موقعیت شغلی، نوع همکاری، سابقه و رزومه PDF را ثبت کند. مدل دارای status برای بررسی درخواست است.

## ۵-۱۲- اطلاع‌رسانی (`notifications` / app label: `sms`)

نام پکیج Django این بخش `notifications` است، اما `AppConfig.label` آن برابر `sms` و نام فارسی آن «پیامک» است. این بخش قالب‌ها و لاگ پیامک، ارسال SMS، و facade اطلاع‌رسانی سفارش را نگهداری می‌کند. `NotificationService` برای رویدادهای سفارش از `SMSService` و `EmailService` استفاده می‌کند، اما شکست ارسال پیام نباید جریان سفارش را متوقف کند.

## ۵-۱۳- Admin

`Admin` بر پایه پنل مدیریت Django توسعه یافته و شامل branding، labelهای فارسی، صفحات عملیاتی، `task` center، kitchen queue، `pickup` screen، order lookup و shift summary است.

## ۵-۱۴- SEO

SEO شامل contextهای عمومی، `robots.txt`، `sitemap.xml` و sitemap برای صفحات `static`، دسته‌بندی و محصولات است. `SITE_URL`، `SITE_NAME` و توضیح پیش‌فرض SEO از تنظیمات محیطی خوانده می‌شوند.

## ۵-۱۵- Infrastructure

زیرساخت شامل تنظیمات جداگانه `dev/prod`، Dockerfile، Docker Compose محلی و تولیدی، Nginx، Gunicorn، Redis، Celery، health checks، backup، restore، SSL و مستندات `deploy` است.

# ۶- فرآیند کلی ثبت سفارش

## ۶-۱- نمای کلی چرخه سفارش

```text
Customer Browser
  -> Website
  -> Product List / Product Detail
  -> Add to Cart
  -> Inventory Validation
  -> Cart Reservation
  -> Checkout
  -> Payment Selection
  -> Order Creation
  -> Stock Reservation for Order
  -> Payment Processing
  -> Preparation
  -> Ready for Pickup
  -> Delivered
  -> Completed Operationally
```

## ۶-۲- مرحله ۱: ورود مشتری به سایت

مشتری وارد سایت می‌شود و از صفحه اصلی یا مسیر فروشگاه، محصولات را مشاهده می‌کند. محصولاتی در کاتالوگ عمومی نمایش داده می‌شوند که وضعیت موجودی آن‌ها `available` است. صفحه اصلی از محصولات featured و سرویس توصیه‌گر برای نمایش پیشنهادها استفاده می‌کند.

## ۶-۳- مرحله ۲: انتخاب محصول

مشتری وارد صفحه محصول می‌شود. در این مرحله رویداد `PRODUCT_VIEW` در `growth` ثبت می‌شود. سیستم می‌تواند محصولات مرتبط یا پیشنهادی را از سرویس‌های `intelligence` نمایش دهد و impression پیشنهادها را ثبت کند.

## ۶-۴- مرحله ۳: افزودن به سبد

در درخواست افزودن به سبد:

- محصول با شناسه ارسال‌شده پیدا می‌شود.
- سبد کاربر از user یا `session` دریافت یا ایجاد می‌شود.
- تعداد به integer تبدیل می‌شود.
- اعتبار تعداد بررسی می‌شود.
- موجود بودن محصول بررسی می‌شود.
- موجودی و ظرفیت با `StockService.check_availability` بررسی می‌شود.
- در صورت موفقیت، `CartItem` ایجاد یا به‌روزرسانی می‌شود.
- برای سبد، رزرو موجودی ایجاد می‌شود.
- رویداد `ADD_TO_CART` در `growth` ثبت می‌شود.

اگر موجودی یا ظرفیت کافی نباشد، پیام فارسی «تعداد درخواستی بیشتر از موجودی قابل فروش است.» به کاربر نمایش داده می‌شود.

## ۶-۵- مرحله ۴: اعتبارسنجی موجودی

موجودی از مدل `ProductInventory` خوانده می‌شود. اگر `track_stock=False` باشد، محصول از نظر موجودی محدود نمی‌شود. اگر `track_stock=True` باشد، مقدار قابل فروش برابر است با:

```text
available_quantity = stock_quantity - reserved_quantity
```

در زمان به‌روزرسانی سبد، رزروهای فعال همان سبد به مقدار قابل استفاده اضافه می‌شوند تا کاربر به دلیل رزرو قبلی خودش با خطای اشتباه مواجه نشود.

## ۶-۶- مرحله ۵: رزرو موجودی برای سبد

پس از افزودن یا تغییر تعداد، رزرو قبلی همان محصول در همان سبد آزاد می‌شود و رزرو جدید ایجاد می‌گردد. مدت رزرو سبد از تنظیم `CART_RESERVATION_MINUTES` می‌آید که مقدار پیش‌فرض آن ۳۰ دقیقه است.

رزروهای منقضی‌شده توسط `task` دوره‌ای `expire-stale-reservations` بررسی و آزاد می‌شوند.

## ۶-۷- مرحله ۶: ورود به checkout

اگر سبد خالی باشد، کاربر به سبد خرید برگردانده می‌شود. اگر سبد کالا داشته باشد، فرم `checkout` نمایش داده می‌شود.

داده‌های `checkout`:

| فیلد | توضیح |
| --- | --- |
| `first_name` | الزامی |
| `phone` | الزامی |
| `email` | اختیاری؛ در صورت خالی بودن ایمیل داخلی ساخته می‌شود |
| `pickup_note` | اختیاری؛ برای شماره میز یا یادداشت |
| `payment_method` | آنلاین یا حضوری |

## ۶-۸- مرحله ۷: پرداخت آنلاین

اگر کاربر پرداخت آنلاین را انتخاب کند:

1. سبد و آیتم‌های سبد با `select_for_update` قفل می‌شوند.
2. اگر `checkout` فعال قبلی برای همان سبد وجود داشته باشد، همان جریان بازگردانده می‌شود.
3. سبد خالی و شماره تماس بررسی می‌شوند.
4. subtotal محاسبه می‌شود.
5. `growth` `checkout` context آماده می‌شود.
6. سفارش با وضعیت `PENDING_PAYMENT` ساخته می‌شود.
7. سفارش به عنوان `active` `checkout` order روی سبد ثبت می‌شود.
8. رزرو سبد آزاد و رزرو سفارش ایجاد می‌شود.
9. سبد پاک می‌شود.
10. Payment با `provider` آنلاین ساخته می‌شود.
11. اگر `provider` Zarinpal باشد، `checkout` `session` از `API` زرین‌پال درخواست می‌شود.
12. کاربر به صفحه redirect پرداخت هدایت می‌شود.

پرداخت آنلاین فقط با currency `irr` معتبر است. برای Zarinpal حداقل مبلغ پرداخت ۱۰۰۰ ریال بررسی می‌شود و مبلغ Payment باید با total سفارش برابر باشد.

## ۶-۹- مرحله ۸: پرداخت حضوری

اگر کاربر پرداخت حضوری را انتخاب کند:

1. سبد قفل می‌شود.
2. شماره تماس الزامی است.
3. سفارش با وضعیت `AWAITING_PAYMENT` ساخته می‌شود.
4. وضعیت پرداخت `PENDING_PAYMENT` است.
5. fulfillment برابر `PICKUP` و هزینه ارسال صفر است.
6. رزرو سفارش ایجاد می‌شود.
7. Payment حضوری با `provider` متناسب ساخته می‌شود.
8. کاربر پیام «سفارش ثبت شد. لطفاً برای پرداخت به صندوق مراجعه کنید.» دریافت می‌کند.

در UI عمومی `checkout` گزینه «پرداخت حضوری» با مقدار `cash` ارسال می‌شود. مقدار `counter_card` در `backend` برای سازگاری و عملیات داخلی حفظ شده است.

## ۶-۱۰- مرحله ۹: ایجاد سفارش

در ایجاد سفارش:

- شماره سفارش با الگوی `CR-YYYYMMDD-RANDOM` ساخته می‌شود.
- کاربر، اطلاعات تماس، notes، روش پرداخت و fulfillment ثبت می‌شود.
- برای `pickup`، فیلدهای آدرس پاک و هزینه ارسال صفر می‌شود.
- هر `CartItem` به `OrderItem` تبدیل می‌شود.
- subtotal و total محاسبه و ذخیره می‌شوند.
- شماره روزانه سفارش اختصاص داده می‌شود.

## ۶-۱۱- مرحله ۱۰: پرداخت و نهایی‌سازی

برای پرداخت آنلاین موفق:

- Payment به `SUCCEEDED` می‌رود.
- وضعیت پرداخت سفارش `PAID` می‌شود.
- رزروهای سفارش confirm می‌شوند.
- سفارش ابتدا به `PAID` و سپس به `CONFIRMED_BY_SHOP` منتقل می‌شود.

برای پرداخت حضوری:

- صندوق دریافت وجه را ثبت می‌کند.
- Payment به `SUCCEEDED` می‌رود.
- وضعیت پرداخت سفارش `PAID` می‌شود.
- رزروهای سفارش confirm می‌شوند.
- سفارش به `PREPARING` منتقل می‌شود.

## ۶-۱۲- مرحله ۱۱: آماده‌سازی

تیم آشپزخانه سفارش‌های معتبر را در kitchen queue می‌بیند. سفارش می‌تواند از `PAID` یا `CONFIRMED_BY_SHOP` وارد `PREPARING` شود. سپس با اقدام `staff` به `PACKAGED` منتقل می‌شود.

## ۶-۱۳- مرحله ۱۲: آماده تحویل

وقتی سفارش `PACKAGED` است، در صفحه `pickup` قابل مشاهده می‌شود. تایم‌لاین مشتری در این مرحله پیام «سفارش شما آماده تحویل از کانتر است.» را نشان می‌دهد.

## ۶-۱۴- مرحله ۱۳: تحویل

با ثبت تحویل از کانتر، سیستم از مسیر `complete_pickup_order` عبور می‌کند. برای سفارش `pickup`، وضعیت ابتدا به `OUT_FOR_DELIVERY` و سپس با `complete_delivery` به `DELIVERED` منتقل می‌شود. در تکمیل تحویل، موجودی confirm شده مصرف و رزروها آزاد می‌شوند.

## ۶-۱۵- مرحله ۱۴: تکمیل عملیاتی

پس از `DELIVERED`، سفارش از صف‌های فعال خارج می‌شود و در گزارش‌ها و تاریخچه سفارش باقی می‌ماند. اگر سفارش نیازمند refund باشد، مسیرهای refund در `OrderService` و `PaymentService` وجود دارند.

## ۷-۳- قوانین ظرفیت تولید روزانه

سیستم برای محصولات capacity روزانه ایجاد یا دریافت می‌کند. در زمان رزرو، ابتدا fulfillment date مناسب پیدا می‌شود. حداکثر بازه بررسی ظرفیت ۱۴ روز است.

قواعد اصلی:

- اگر ظرفیت روز جاری کافی باشد، همان روز انتخاب می‌شود.
- اگر ظرفیت کافی نباشد، روزهای بعد تا ۱۴ روز بررسی می‌شوند.
- اگر در این بازه ظرفیت کافی پیدا نشود، `CapacityExceededError` ایجاد می‌شود.
- اگر محصول `allow_preorder=True` باشد، سیستم تلاش می‌کند ظرفیت آینده را در نظر بگیرد.
- ظرفیت پیش‌فرض برای محصول stock-tracked برابر `max(stock_quantity, 50)` است.
- ظرفیت پیش‌فرض برای محصول بدون track stock برابر ۱۰۰ است.

# ۸- معماری کلی

## ۸-۱- نمای معماری تولیدی

```text
Browser
  -> Nginx
  -> Gunicorn
  -> Django
  -> PostgreSQL

Django
  -> Redis cache/session
  -> Redis broker
  -> Celery worker
  -> Celery beat

Nginx
  -> static files
  -> media files
  -> TLS termination
```

## ۸-۲- مسئولیت هر لایه

| لایه | مسئولیت |
| --- | --- |
| Browser | نمایش صفحات `HTML/CSS/JS`، ارسال فرم‌ها، دریافت پیام‌ها و redirect پرداخت |
| Nginx | reverse proxy، سرو فایل‌های `static/media`، TLS، webroot چالش Certbot |
| Gunicorn | اجرای `WSGI` application و مدیریت workerهای Django |
| Django | منطق دامنه، routing، `templates`، `admin`، forms، services، ORM و validation |
| PostgreSQL | ذخیره داده‌های اصلی شامل کاربران، محصولات، سبد، سفارش، پرداخت، موجودی و گزارش‌ها |
| Redis | `cache`، `session` `cache` در تولید، broker و result `backend` برای Celery |
| Celery Worker | اجرای `task`های پس‌زمینه مانند SMS، analytics، انقضای رزروها و cleanup پرداخت‌ها |
| Celery Beat | زمان‌بندی دوره‌ای `task`ها |
| Sentry | دریافت خطاها و tracing اختیاری در تولید |

## ۸-۳- معماری Django

پروژه از معماری app-based استفاده می‌کند. هر اپلیکیشن مسئول بخشی از دامنه است و ارتباط بین اپ‌ها عمدتاً از طریق مدل‌ها و serviceهای صریح انجام می‌شود.

اصول معماری:

- منطق حساس در serviceها نگهداری می‌شود، نه فقط view یا `admin`.
- عملیات سفارش از طریق `OrderService` کنترل می‌شود.
- عملیات پرداخت از طریق `PaymentService` کنترل می‌شود.
- عملیات موجودی از طریق `StockService` و سرویس‌های `inventory` کنترل می‌شود.
- `checkout` از transaction و lock استفاده می‌کند.
- خطاهای قابل انتظار به پیام‌های فارسی کاربر تبدیل می‌شوند.

# ۱۱- فناوری‌های استفاده‌شده

| فناوری | دلیل انتخاب و نقش در پروژه |
| --- | --- |
| Django | فریم‌ورک اصلی `backend` است؛ ORM، `admin`، forms، routing، `templates`، auth و security primitives را یکپارچه ارائه می‌کند. برای پروژه‌ای که هم فروشگاه عمومی و هم پنل مدیریت عملیاتی دارد، انتخاب مناسبی است. |
| Python 3.12 | زبان `runtime` پروژه است و با اکوسیستم Django، Celery، pytest و کتابخانه‌های پرداخت/HTTP سازگار است. |
| PostgreSQL | پایگاه داده اصلی است. داده‌های رابطه‌ای سفارش، پرداخت، موجودی، کاربر و گزارش‌های عملیاتی نیازمند transaction، constraint و queryهای قابل اتکا هستند. |
| `psycopg2-binary` | adapter پایگاه داده PostgreSQL برای اتصال Django به PostgreSQL است. |
| Redis و `django-redis` | در محیط تولید برای `cache/session` و همچنین `broker/result` `backend` مربوط به Celery استفاده می‌شود. |
| `celery[redis]` | `task`های پس‌زمینه مانند ارسال SMS، cleanup پرداخت‌ها، انقضای رزروها، analytics و `intelligence` با Celery اجرا می‌شوند تا جریان request کاربر کند یا وابسته به عملیات زمان‌بر نشود. |
| Gunicorn | application server تولیدی برای اجرای Django `WSGI` است و پشت Nginx قرار می‌گیرد. |
| Nginx | reverse proxy، سرو `static/media`، TLS و مسیرهای Certbot را مدیریت می‌کند. |
| Docker | محیط اجرای قابل تکرار برای web، worker و سایر سرویس‌ها فراهم می‌کند. |

| WhiteNoise | fallback اختیاری برای سرو `static` files زمانی است که Nginx مستقیماً `static` را سرو نمی‌کند. |

# ۱۲- ویژگی‌های فنی

## ۱۲-۱- آمادگی تولید

پروژه دارای اجزای اصلی لازم برای اجرای تولیدی است:

- تنظیمات جداگانه dev و prod
- اجباری بودن `DEBUG=False` در محیط تولید
- Dockerfile
- Docker Compose تولیدی
- Gunicorn
- Nginx
- PostgreSQL
- Redis
- Celery worker و Celery beat
- health/readiness endpoints
- اسکریپت `deploy`
- اسکریپت backup و restore
- مستندات launch و VPS
- تست‌های گسترده

آمادگی تولید به معنی آماده بودن کد و فرآیندهای فنی است، نه آماده بودن خود زیرساخت محیط تولید. دامنه، secrets، merchant ID، VPS و تنظیمات واقعی باید پیش از go-live تکمیل شوند.

## ۱۲-۲- Docker

Dockerfile از `python:3.12-slim-bookworm` استفاده می‌کند، وابستگی‌ها را نصب می‌کند، کد را copy می‌کند و اجرای پیش‌فرض را به Gunicorn می‌سپارد.

Docker Compose محلی:

- `db`
- `web`

Docker Compose تولیدی:

- `db`
- `redis`
- `web`
- `celery_worker`
- `celery_beat`
- `nginx`

## ۱۲-۳- Health Checks

مسیرهای سلامت:

| Endpoint | هدف |
| --- | --- |
| `/health/` | liveness؛ بررسی زنده بودن process بدون وابستگی DB/Redis |
| `/ready/` | Readiness؛ بررسی آمادگی وابسته به DB و Redis |
| `/health/full/` | بررسی کامل‌تر برای عیب‌یابی؛ در محیط تولید به‌صورت پیش‌فرض `404` برمی‌گرداند و فقط با `HEALTH_FULL_ENABLED=true` فعال می‌شود |

## ۱۲-۴- Readiness

Readiness برای سناریوهای `deploy` و orchestration مهم است. در Docker Compose تولیدی، `healthcheck` کانتینر `web` از `/health/` استفاده می‌کند. اسکریپت `deploy/healthcheck.sh` نیز liveness، `static` file، `robots.txt` و `sitemap.xml` را بررسی می‌کند. بررسی `/ready/` در `runbook` و اسکریپت `deploy/staging-smoke-test.sh` انجام می‌شود. این تفکیک باعث می‌شود زنده بودن process و آماده بودن سرویس برای پاسخ به traffic جداگانه سنجیده شوند.

## ۱۲-۵- Structured Logging

پروژه از logging داخلی Django و helperهای Observability برای ثبت eventهای سفارش و پرداخت استفاده می‌کند. در خطاهای پرداخت، اطلاعات حساس مانند merchant ID پاک یا mask می‌شوند. برای `task`های پس‌زمینه نیز `BackgroundTaskLog` وجود دارد.

## ۱۲-۶- Backups

اسکریپت `deploy/backup.sh` برای backup دیتابیس و `media` وجود دارد. مستند `docs/BACKUP_RESTORE.md` سیاست backup/restore را توضیح می‌دهد. restore عملیات destructive است و نیازمند تأیید صریح است.

## ۱۲-۷- Security

قابلیت‌های امنیتی مهم:

- اجباری بودن `DEBUG=False` در محیط تولید
- کنترل `ALLOWED_HOSTS`
- پشتیبانی از `CSRF_TRUSTED_ORIGINS`
- secure `cookie`ها هنگام فعال بودن HTTPS
- HSTS پس از فعال‌سازی HTTPS
- `X_FRAME_OPTIONS = DENY`
- `SECURE_CONTENT_TYPE_NOSNIFF`
- `SECURE_REFERRER_POLICY`
- اعتبارسنجی upload رزومه PDF در `careers`
- عدم commit فایل `.env` و backup archives طبق مستندات launch
- mask کردن داده‌های حساس در لاگ خطاهای Zarinpal

# ۱۳- قابلیت توسعه

## ۱۳-۳- قابلیت افزودن Feature جدید

در `payments` و `notifications` ساختار `provider` وجود دارد. برای افزودن `provider` پرداخت یا SMS:

- ثبت لاگ‌های بدون داده حساس

## ۱۳-۵- قابلیت نگهداری

عوامل نگهداری‌پذیری:

- transaction در عملیات حساس
- service layer برای منطق مشترک
- تست‌های گسترده
- مستندات استقرار و backup
- تفکیک `dev/prod` settings
- استفاده از environment variables
- عدم وابستگی viewها به `provider` خاص پرداخت

# ۱۵- جمع‌بندی

Crumbs یک سامانه تولیدی برای مدیریت سفارش‌گیری، پرداخت، موجودی و عملیات کافه/بیکری است. پروژه از نظر کد، ساختار دامنه، سرویس‌های اصلی، جریان `checkout`، کنترل موجودی، پرداخت، عملیات آشپزخانه/کانتر، داشبوردهای مدیریتی، زیرساخت Docker و مستندات استقرار آماده تحویل و ادامه توسعه است.

نقطه قوت فنی پروژه در تفکیک دامنه‌ها، استفاده از transaction برای عملیات حساس، کنترل رزرو موجودی، state machine سفارش، service layer و آمادگی استقرار تولیدی است. این ساختار برای تحویل پروژه به یک شرکت نرم‌افزاری دیگر مناسب است، زیرا مسئولیت هر اپلیکیشن، جریان‌های اصلی و نیازمندی‌های تولیدی قابل شناسایی و پیگیری هستند.

Crumbs در وضعیت آمادگی تولید قرار دارد، اما راه‌اندازی نهایی آن به تکمیل زیرساخت محیط تولید وابسته است: دامنه، VPS، secrets، merchant ID، SMS `credentials`، HTTPS، backup off-server و اجرای برنامه تست launch.
