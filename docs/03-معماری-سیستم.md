# 1- نمای کلی معماری

Crumbs یک پروژه Django 5.2 با معماری app-based، پایگاه‌داده PostgreSQL، `cache` و broker مبتنی بر Redis، پردازش پس‌زمینه با Celery، اجرای production با Gunicorn و reverse proxy با Nginx است. رابط کاربری عمومی و پنل مدیریت با templateهای Django، فایل‌های `static` و JavaScript/CSS پروژه پیاده‌سازی شده‌اند.

نمای عملیاتی production در `docker-compose.production.yml` چنین است:

```text
Browser
  |
  v
Nginx
  |
  v
Gunicorn
  |
  v
Django
  |----------------------.
  |                      |
  v                      v
PostgreSQL             Redis
  |                      |
  |                      v
  '------------------> Celery Worker
                         ^
                         |
                    Celery Beat
```

نمای ساده‌شده‌ای که مسئولیت هر لایه را نشان می‌دهد:

```text
Browser
  |
  |  HTTP/HTTPS request, form POST, session cookie
  v
Nginx
  |
  |  reverse proxy, static/media serving, TLS termination
  v
Gunicorn
  |
  |  WSGI process manager for Django
  v
Django
  |
  |  URL routing, middleware, views, services, ORM, templates, admin
  +--------------------+----------------------+
  |                    |                      |
  v                    v                      v
PostgreSQL            Redis                 Celery
persistent data       cache/session/broker  background jobs
```

| لایه | پیاده‌سازی در مخزن | مسئولیت |
| --- | --- | --- |
| Browser | templateهای `templates/`، CSS در `static/css/crumbs.css`، JS در `static/js/crumbs.js` | نمایش صفحات عمومی، `checkout`، حساب کاربری، `cart`، `wishlist` و تعامل‌های فرم. |
| Nginx | `docker/nginx/nginx.conf` و templateهای `docker/nginx/conf.d/` | reverse proxy به `web:8000`، سرو `static/media`، پشتیبانی SSL با Certbot. |
| Gunicorn | `docker/gunicorn.conf.py` و CMD در `docker/Dockerfile` | اجرای `config.wsgi:application` در محیط production. |
| Django | `config/`، `apps/`، `templates/` | منطق HTTP، دامنه، `admin`، ORM، فرم‌ها، سرویس‌ها، `task` dispatch و security middleware. |
| PostgreSQL | `DATABASES` در `config/settings/base.py`، سرویس `db` در production compose | ذخیره مدل‌های دامنه، تراکنش‌ها، constraintها و داده‌های عملیاتی. |
| Redis | `REDIS_URL`، `CELERY_BROKER_URL`، سرویس `redis` | `cache`، `session` `cache` alias، broker و result `backend` برای Celery. |
| Celery | `config/celery.py`، `CELERY_BEAT_SCHEDULE`، سرویس‌های `celery_worker` و `celery_beat` | پردازش پیامک، cleanup، analytics، `intelligence`، `loyalty` و `task`های زمان‌بندی‌شده. |

نکات اختیاری و Legacy در سطح معماری:

| بخش | وضعیت | توضیح |
| --- | --- | --- |
| Stripe | اختیاری | `provider` پرداخت در کد وجود دارد اما در production به‌صورت پیش‌فرض غیرفعال است و با `STRIPE_ENABLED` کنترل می‌شود. |
| WhiteNoise | اختیاری | fallback سرو `static` در production است و فقط با `USE_WHITENOISE=True` وارد middleware می‌شود. |
| `Delivery/COD` قدیمی | Legacy | مدل‌ها و وضعیت‌های مرتبط با ارسال و COD برای سازگاری نگهداری شده‌اند؛ جریان فعال عمومی `checkout` بر `pickup` و پرداخت آنلاین/حضوری متمرکز است. |
| `/health/full/` | اختیاری | در `DEBUG=True` فعال است؛ در production فقط با `HEALTH_FULL_ENABLED=true` پاسخ diagnostics می‌دهد. |

# 3- معماری دامنه (Domain Architecture)

## 3-1- جدول دامنه اپلیکیشن‌ها

| App | Purpose | Main Models | Main Services | Dependencies | Used by | Business Responsibility |
| --- | --- | --- | --- | --- | --- | --- |
| `accounts` | مدیریت حساب کاربری، پروفایل و آدرس | `CustomerProfile`، `Address` | `resolve_login_identifier`، `merge_session_cart_on_login`، `get_checkout_initial` | Django `User`، `cart`، `orders` | `login/register`، profile، `checkout`، order history | نگهداری هویت مشتری، اطلاعات تماس و داده اولیه `checkout`. |
| `cart` | سبد خرید کاربر/مهمان و آماده‌سازی `checkout` | `Cart`، `CartItem` | `get_or_create_cart`، `add_item`، `lock_cart_for_checkout`، `clear_cart`، `merge_carts` | `products`، `inventory`، `orders` | صفحات `cart/checkout`، login merge | جمع‌آوری اقلام سفارش و حفاظت از mutation هنگام `checkout` فعال. |

# 6- Checkout Architecture

## 6-1- نمای کلی checkout

```text
Cart
  |
  v
Validation
  |
  v
Inventory Check
  |
  v
Reservation
  |
  v
Order Creation
  |
  v
Payment
  |
  v
Confirmation
```

مسیر HTTP اصلی `checkout` در `core.views.checkout` پیاده‌سازی شده است. این view فرم `core.forms.CheckoutForm` را پردازش می‌کند و بر اساس روش پرداخت، orchestration را به سرویس دامنه مناسب می‌سپارد: پرداخت آنلاین به `delivery.services.process_checkout` و پرداخت حضوری به `orders.services.counter_checkout.process_counter_checkout`. گزینه‌های عمومی پرداخت `online` و `cash` هستند. مقدار `counter_card` در `backend` وجود دارد، اما در فرم عمومی `checkout` فعلی exposed نشده است.

## 6-2- اجزای checkout

| جزء | کد | نقش |
| --- | --- | --- |
| Cart loading | `core.views._get_cart` و `cart.services.get_or_create_cart` | یافتن یا ساخت سبد بر اساس user یا `session`. |
| Form validation | `CheckoutForm` | اعتبارسنجی اطلاعات مشتری، شماره تماس، ایمیل اختیاری و روش پرداخت. |
| Online `checkout` orchestration | `DeliveryServiceCheckout.process_checkout` | قفل `cart`، بررسی `checkout` فعال، آماده‌سازی `growth` context، ساخت order، اعمال `growth`، finalization موجودی و شروع پرداخت آنلاین. |
| Cart lock | `cart.services.lock_cart_for_checkout` | قفل کردن `cart` و خواندن `CartItem`ها با `select_for_update`. |
| Order creation | `orders.services.create_order_from_cart` | ساخت `Order`، `OrderItem`، شماره سفارش و شماره روزانه. |
| Stock finalization | `orders.services.finalize_checkout_stock` | آزادسازی رزرو `cart`، رزرو برای order و clear سبد. |
| Online payment | `PaymentService.initiate_online` | ساخت یا reuse پرداخت زرین‌پال `processing` و ایجاد `checkout` `URL`. |
| Cash payment | `CounterCheckoutService.process_checkout` | ساخت سفارش `awaiting_payment` و Payment حضوری `pending`. |
| Access grant | `grant_checkout_order_access` | ثبت دسترسی `session` برای مشاهده `confirmation/receipt` توسط مهمان. |

## 6-3- Checkout آنلاین

```text
POST /checkout/
  |
  v
CheckoutForm(payment_method=online)
  |
  v
DeliveryServiceCheckout.process_checkout(cart, customer, user=user)
  |
  +--> cart_services.lock_cart_for_checkout
  +--> _resolve_in_progress_checkout
  +--> GrowthCheckoutFacade.prepare
  +--> create_order_from_cart(status=pending_payment)
  +--> cart_services.set_active_checkout_order
  +--> GrowthCheckoutFacade.apply_to_order
  +--> finalize_checkout_stock(cart, order)
  '--> PaymentService.initiate_online(order)
  |
  v
Payment(status=processing, provider=zarinpal)
  |
  v
checkout_url
  |
  v
Redirect to provider checkout_url
```

رفتارهای مهم:

| موضوع | رفتار واقعی |
| --- | --- |
| `provider` پیش‌فرض | `zarinpal` در production مگر env مقدار دیگری تنظیم کند. |
| currency | `ONLINE_PAYMENT_CURRENCY` باید `irr` باشد. |
| reuse پرداخت | اگر پرداخت زرین‌پال `processing` با authority و `checkout` `URL` معتبر وجود داشته باشد، reuse می‌شود. |
| cleanup | پرداخت آنلاین stale بعد از ۳۰ دقیقه با `task` پاک‌سازی می‌شود. |
| موفقیت | `callback` موفق payment را `succeeded` و order را `paid` سپس `confirmed_by_shop` می‌کند. |
| شکست | `callback` ناموفق یا verify ناموفق payment را `failed` و order را cancel می‌کند. |

## 6-4- Checkout پرداخت حضوری

```text
POST /checkout/
  |
  v
CheckoutForm(payment_method=cash)
  |
  v
CounterCheckoutService.process_checkout(...)
  |
  v
create_order_from_cart(
  initial_status=awaiting_payment,
  initial_payment_status=pending_payment
)
  |
  v
finalize_checkout_stock(cart, order)
  |
  v
PaymentService.initiate_counter_payment(order, cash)
  |
  v
Payment(status=pending, provider=cash)
  |
  v
Confirmation page
```

تکمیل پرداخت حضوری از `admin` action سفارش انجام می‌شود:

```text
OrderAdmin.mark_cash_received
  |
  v
PaymentService.mark_counter_cash_received
  |
  v
OrderService.finalize_counter_payment
  |
  +--> payment_status = paid
  +--> StockService.confirm_reservations
  '--> status = preparing
```

## 6-5- خطا و cleanup در checkout

| خطا | رفتار |
| --- | --- |
| سبد خالی | `checkout` رد می‌شود و کاربر به `cart` برگردانده می‌شود. |
| محصول unavailable | `CheckoutError` از validation رخ می‌دهد. |
| کمبود موجودی | `StockService.check_availability` خطا می‌دهد. |
| خطای `checkout` پس از order creation | cleanupهای `cart` lock و reservation در مسیرهای مربوطه انجام می‌شود. |
| پرداخت آنلاین stale | `cleanup_stale_online_payment` payment را `failed` و order را `cancelled` می‌کند و `cart` `checkout` lock را پاک می‌کند. |

# 7- Payment Architecture

## 7-1- مدل پرداخت

| مدل | نقش |
| --- | --- |
| `Payment` | وضعیت مالی مرتبط با یک `Order`؛ شامل `provider`، status، amount، currency، `provider` IDs، `checkout` `URL`، failure message و metadata. |
| `PaymentEvent` | ثبت رویداد `provider` با `event_id` یکتا، نوع رویداد، payload، وضعیت پردازش و خطا. |

مقادیر واقعی:

| enum | values |
| --- | --- |
| `Payment.Provider` | `zarinpal`، `stripe`، `cod`، `cash`، `counter_card` |
| `Payment.Status` | `pending`، `processing`، `succeeded`، `failed`، `cancelled`، `refunded` |

## 7-2- Provider abstraction

انتخاب `provider` آنلاین از `payments.services.get_online_payment_provider` انجام می‌شود:

```text
settings.DEFAULT_PAYMENT_PROVIDER
  |
  +--> zarinpal -> ZarinpalPaymentProvider
  |
  +--> stripe   -> StripePaymentProvider اگر STRIPE_ENABLED=True
```

Stripe اختیاری است. اگر `DEFAULT_PAYMENT_PROVIDER=stripe` باشد ولی `STRIPE_ENABLED=False`، `PaymentConfigurationError` رخ می‌دهد. در `config/settings/prod.py` پیش‌فرض production روی زرین‌پال تنظیم شده است.

## 7-3- Zarinpal flow

```text
PaymentService.initiate_online(order)
  |
  v
ZarinpalPaymentProvider.create_checkout_session(order, payment)
  |
  v
POST request to Zarinpal request API
  |
  v
authority received
  |
  v
Payment.provider_checkout_session_id = authority
Payment.provider_payment_id = authority
Payment.checkout_url = /pg/StartPay/<authority>
Payment.status = processing
```

وابستگی‌های production:

| env | نقش |
| --- | --- |
| `ZARINPAL_MERCHANT_ID` | merchant id برای `request/verify`. |
| `ZARINPAL_CALLBACK_URL` | `callback` `URL` اعلامی به `provider`. |
| `ZARINPAL_SANDBOX` | تعیین `sandbox/production` `API`. |
| `DEFAULT_PAYMENT_PROVIDER` | انتخاب `zarinpal`. |

## 7-4- Callback flow

```text
GET /payments/zarinpal/callback/?Authority=...&Status=...
  |
  v
payments.views.zarinpal_callback
  |
  v
Payment lookup by provider_checkout_session_id
  |
  v
handle_zarinpal_callback(payload)
  |
  v
PaymentEvent(event_id="zarinpal:authority:<authority>")
  |
  v
ZarinpalPaymentProvider.handle_webhook_event
  |
  +--> status != OK -> mark_order_payment_failed
  |
  +--> status == OK -> verify payment
                         |
                         v
                       mark_order_paid
                         |
                         v
                       OrderService.finalize_online_payment
```

## 7-5- Failure flow

```text
Provider callback failure
  |
  v
PaymentService.mark_failed
  |
  +--> Payment.status = failed
  +--> Payment.failure_message = reason
  |
  v
OrderService.mark_payment_failed
  |
  +--> StockService.release_reservations
  +--> Order.payment_status = failed
  '--> Order.status = cancelled
```

در `OrderService.mark_payment_failed` اگر سفارش قبلاً `paid` یا `cash_received` باشد، مسیر شکست پرداخت سفارش را تغییر نمی‌دهد.

## 7-6- Cash flow

پرداخت حضوری در معماری پرداخت از `provider`های `cash` و `counter_card` استفاده می‌کند:

```text
CounterCheckoutService.process_checkout
  |
  v
PaymentService.initiate_counter_payment
  |
  v
Payment(provider=cash, status=pending)
  |
  v
Admin action: mark_cash_received
  |
  v
PaymentService.mark_counter_cash_received
  |
  v
Payment.status = succeeded
  |
  v
OrderService.finalize_counter_payment
```

`counter_card` در `backend` حفظ شده است، اما در UI عمومی `checkout` فعلی به‌عنوان گزینه نمایش داده نمی‌شود.

## 7-7- Reuse of processing payment

برای زرین‌پال، `PaymentService._get_reusable_zarinpal_payment` آخرین پرداخت `processing` را که authority و `checkout` `URL` دارد پیدا می‌کند. اگر amount یا currency آن با سفارش ناسازگار باشد، خطا صادر می‌شود؛ در غیر این صورت همان Payment برگردانده می‌شود. این رفتار از ساخت `checkout`های موازی و تکراری برای یک order جلوگیری می‌کند.

## 7-8- Validation

| اعتبارسنجی | محل |
| --- | --- |
| currency آنلاین باید `irr` باشد | `PaymentService.initiate_online` |
| سفارش پرداخت‌شده دوباره پرداخت نمی‌شود | `PaymentService.initiate_online` |
| `provider` Stripe باید فعال باشد | `get_online_payment_provider` |
| `callback` زرین‌پال باید authority داشته باشد | `payments.views.zarinpal_callback` و `provider` |
| پرداخت حضوری فقط برای order counter payment مجاز است | `PaymentService.initiate_counter_payment` |
| payment باید به همان order تعلق داشته باشد | `PaymentService._mark_counter_payment_received` و COD methods |
| داده حساس در log پرداخت ثبت نشود | `core.observability.log_payment_event` و redaction `provider` زرین‌پال |

| `DailyProductionCapacity` | ظرفیت تولید هر محصول برای هر تاریخ؛ شامل `max_units`، `reserved_units` و `fulfilled_units`. |
| `StockReservation` | رزرو موجودی برای `cart` یا order؛ شامل product، order، `cart`، `quantity`، production date، status و expires_at. |

مقادیر `StockReservation.Status`:

| مقدار | شرح |
| --- | --- |
| `active` | رزرو فعال و قابل `confirm/release/expire`. |
| `confirmed` | رزرو پس از پرداخت موفق یا دریافت پرداخت حضوری تأیید شده است. |
| `released` | رزرو آزاد شده و از reserved `quantity/capacity` کم شده است. |
| `expired` | رزرو `active` منقضی شده و سپس `expired` علامت خورده است. |

# 9- Order Lifecycle

## 9-1- وضعیت‌های Order

| مقدار | توضیح عملیاتی |
| --- | --- |
| `pending_payment` | سفارش ایجاد شده و منتظر پرداخت آنلاین یا تکمیل پرداخت است. |
| `awaiting_payment` | سفارش پرداخت حضوری در انتظار پرداخت در صندوق است. |
| `paid` | پرداخت آنلاین موفق ثبت شده است. |
| `confirmed_by_shop` | سفارش توسط سیستم یا فروشگاه برای آماده‌سازی تأیید شده است. |
| `preparing` | سفارش در حال آماده‌سازی است. |
| `packaged` | سفارش آماده تحویل از کانتر است. |
| `out_for_delivery` | وضعیت `legacy` برای ارسال. |
| `delivered` | سفارش تحویل داده شده یا `pickup` تکمیل شده است. |
| `cancelled` | سفارش لغو شده است. |
| `refunded` | سفارش مسترد شده است. |

## 9-2- وضعیت‌های پرداخت سفارش

| مقدار | توضیح |
| --- | --- |
| `pending_payment` | پرداخت در انتظار انجام است. |
| `paid` | پرداخت آنلاین یا counter payment نهایی شده است. |
| `cod_pending` | وضعیت `legacy` برای COD در انتظار تأیید. |
| `cod_confirmed` | وضعیت `legacy` برای COD تأیید شده. |
| `cash_received` | نقد دریافت شده است. |
| `failed` | پرداخت شکست خورده است. |
| `refund_requested` | درخواست استرداد ثبت شده است. |
| `refund_processed` | استرداد پردازش شده است. |

## 9-3- روش‌های پرداخت سفارش

| مقدار | وضعیت |
| --- | --- |
| `online` | فعال در `checkout` عمومی. |
| `cash` | فعال در `checkout` عمومی به‌عنوان پرداخت حضوری. |
| `counter_card` | `backend` compatibility؛ در فرم عمومی `checkout` نمایش داده نمی‌شود. |
| `cod` | Legacy؛ برای سازگاری و `admin` actions قدیمی نگهداری شده است. |

## 9-4- جدول کامل transition

transitionها در `delivery.state_machine.ALLOWED_TRANSITIONS` تعریف شده‌اند.

| وضعیت فعلی | وضعیت‌های مجاز بعدی |
| --- | --- |
| `pending_payment` | `paid`، `confirmed_by_shop`، `cancelled` |
| `awaiting_payment` | `preparing`، `cancelled` |
| `paid` | `confirmed_by_shop`، `cancelled`، `refunded` |
| `confirmed_by_shop` | `preparing`، `cancelled`، `refunded` |
| `preparing` | `packaged`، `cancelled`، `refunded` |
| `packaged` | `out_for_delivery`، `cancelled`، `refunded` |
| `out_for_delivery` | `delivered`، `cancelled`، `refunded` |
| `delivered` | `refunded` |
| `cancelled` | بدون transition خروجی |
| `refunded` | بدون transition خروجی |

وضعیت‌های terminal در state machine:

```text
cancelled
refunded
delivered
```

## 9-5- نقش OrderService

`OrderService` تنها نقطه mutation رسمی lifecycle سفارش است:

| متد | نقش |
| --- | --- |
| `transition` | lock سفارش، validate transition، ذخیره status و ساخت `OrderStatusLog`. |
| `cancel` | release رزروها، تغییر payment status در حالت لازم و transition به `cancelled`. |
| `mark_payment_failed` | release رزروها، payment status `failed` و transition به `cancelled`. |
| `request_refund` | ثبت `refund_requested` بدون تغییر status اصلی. |
| `process_refund` | پردازش refund، release stock و transition به `refunded`. |
| `complete_delivery` | مصرف رزروها و transition به `delivered`. |
| `finalize_counter_payment` | payment status را `paid` می‌کند، رزروها را confirm می‌کند و status را `preparing` می‌کند. |
| `finalize_online_payment` | payment status را `paid` می‌کند، رزروها را confirm می‌کند، status را `paid` و سپس `confirmed_by_shop` می‌کند. |
| `finalize_cod_placement`، `confirm_cod`، `record_cash_received` | مسیرهای `legacy` COD. |

## 9-6- لاگ وضعیت

هر transition رسمی در `OrderStatusLog` ذخیره می‌شود:

| فیلد | نقش |
| --- | --- |
| `order` | سفارش هدف. |
| `from_status` | وضعیت قبلی. |
| `to_status` | وضعیت جدید. |
| `note` | توضیح transition. |
| `actor` | عامل تغییر؛ مانند `system` یا username `staff`. |
| `created_at` | زمان ثبت. |

# 12- Security Architecture

## 12-1- CSRF

`CsrfViewMiddleware` در middlewareهای مشترک فعال است. `CSRF_TRUSTED_ORIGINS` از environment خوانده می‌شود و در صورت `ENABLE_HTTPS=True` در production باید تنظیم شده باشد. فرم‌های عمومی `checkout`، login، register، `cart` و `wishlist` از POST و CSRF استفاده می‌کنند.

استثناهای واقعی:

| Endpoint | decorator | توضیح |
| --- | --- | --- |
| `/payments/webhooks/stripe/` | `@csrf_exempt` | `webhook` خارجی Stripe؛ امضا با Stripe `provider` بررسی می‌شود. |
| `/payments/zarinpal/callback/` | `@csrf_exempt` و `@require_GET` | `callback` زرین‌پال بر اساس `authority/status` و `provider` validation پردازش می‌شود. |

## 12-2- Sessions

| تنظیم | مقدار |
| --- | --- |
| `SESSION_ENGINE` | `django.contrib.sessions.backends.cached_db` |
| `SESSION_CACHE_ALIAS` | `default` |
| `SESSION_COOKIE_HTTPONLY` در production | `True` |
| `SESSION_COOKIE_SAMESITE` در production | `Lax` |
| `SESSION_COOKIE_SECURE` | با `ENABLE_HTTPS=True` برابر `True` می‌شود. |

Session برای سبد خرید مهمان، دسترسی به `checkout` order، table `session` و پیام‌های Django استفاده می‌شود.

## 12-3- Authentication و Authorization

| بخش | کنترل |
| --- | --- |
| حساب کاربری | Django auth؛ `LOGIN_URL = "accounts:login"`. |
| order history | فقط کاربر واردشده سفارش‌های خود را می‌بیند. |
| `receipt/confirmation` | `can_view_checkout_order` دسترسی user یا `session` `checkout` را بررسی می‌کند. |

| `kitchen/pickup` actions | `staff`-only و POST-only. |

## 12-4- Cookies و HTTPS

در `config/settings/prod.py`:

| تنظیم | رفتار |
| --- | --- |
| `DEBUG` | همیشه `False` و اگر env `DEBUG=True` باشد خطا می‌دهد. |
| `ALLOWED_HOSTS` | اگر فقط localhost باشد، بدون `LOCAL_PROD_DRY_RUN=True` خطا می‌دهد. |
| `ENABLE_HTTPS=True` | `SECURE_SSL_REDIRECT`، secure `cookies` و HSTS را فعال می‌کند. |
| `SECURE_PROXY_SSL_HEADER` | `("HTTP_X_FORWARDED_PROTO", "https")` |
| `SECURE_CONTENT_TYPE_NOSNIFF` | `True` |
| `X_FRAME_OPTIONS` | `DENY` |
| `SECURE_REFERRER_POLICY` | `strict-origin-when-cross-origin` |

## 12-5- Secrets و Environment variables

secretها در کد hard-code نشده‌اند و از `.env/environment` خوانده می‌شوند. `SECRET_KEY` در base settings اجباری است و اگر مقدار نداشته باشد، settings خطا می‌دهد.

گروه‌های environment:

| گروه | متغیرها |
| --- | --- |
| Django | `SECRET_KEY`، `DEBUG`، `ALLOWED_HOSTS`، `CSRF_TRUSTED_ORIGINS`، `SITE_URL` |

## 12-6- Logging و masking داده حساس

`core.observability` شامل موارد زیر است:

| جزء | نقش |
| --- | --- |
| `OPS_LOG_FIELDS` | فقط فیلدهای عملیاتی مجاز مثل `order_id`، `payment_id`، `status` و `task_id` را وارد JSON log می‌کند. |

زرین‌پال `provider` نیز response body و متن خطا را با helperهای redaction محدود و پاک‌سازی می‌کند.

# 18- Design Principles

## 18-1- Service Layer

پروژه برای عملیات حساس از service layer استفاده می‌کند. نمونه‌های واقعی:

| اصل | نمونه |
| --- | --- |
| view سبک‌تر | `core.views.checkout` داده فرم و routing را کنترل می‌کند و mutationها را به `DeliveryServiceCheckout` یا `CounterCheckoutService` می‌سپارد. |
| mutation سفارش در service | `OrderService` مسئول transition، cancel، refund، payment finalization و stock handling است. |
| پرداخت در service | `PaymentService` ساخت Payment، `provider` selection، `callback` result و counter payment را متمرکز می‌کند. |
| موجودی در service | `inventory.services` رزرو، release، confirm، fulfill و expire را متمرکز می‌کند. |

## 18-2- App-based architecture

هر دامنه در app جدا نگهداری می‌شود. این جداسازی باعث می‌شود تغییر product، `cart`، payment، `inventory`، `growth` یا `intelligence` مرز مشخص داشته باشد. وابستگی‌ها از طریق مدل‌ها و serviceهای public انجام می‌شود، نه با قرار دادن همه منطق در viewها.

## 18-3- Transactions

مسیرهای حساس مالی و موجودی با `transaction.atomic` و `select_for_update` محافظت شده‌اند. این اصل در `checkout`، order lifecycle، payment `callback`، stock reservation و stale cleanup دیده می‌شود.

## 18-4- Business services

قوانین کسب‌وکار در serviceهای مشخص آمده‌اند:

| قانون | محل |
| --- | --- |
| transition معتبر سفارش | `delivery.state_machine` |
| نهایی‌سازی پرداخت آنلاین | `OrderService.finalize_online_payment` |
| نهایی‌سازی پرداخت حضوری | `OrderService.finalize_counter_payment` |
| جلوگیری از over-reservation | `inventory.services._reserve_item` |
| اعمال کوپن | `growth.coupon_service.CouponService` |
| پیشنهادهای rule-based | `intelligence.recommendation_service` و `intelligence.personalization_service` |

## 18-5- Environment-based configuration

پروژه برای production به environment متکی است. این تصمیم در موارد زیر دیده می‌شود:

| بخش | نمونه |
| --- | --- |
| database | `POSTGRES_*` |
| Redis/Celery | `REDIS_URL` و `CELERY_BROKER_URL` |
| payment | `DEFAULT_PAYMENT_PROVIDER`، `ZARINPAL_*`، `STRIPE_*` |
| security | `ENABLE_HTTPS`، `ALLOWED_HOSTS`، `CSRF_TRUSTED_ORIGINS` |
| Observability | `SENTRY_DSN`، `LOG_LEVEL` |
| SMS | `SMS_PROVIDER`، `KAVENEGAR_API_KEY` |

## 18-6- Dockerized deployment

production stack در `docker-compose.production.yml` مستقل و تکرارپذیر است. همه سرویس‌های `runtime` اصلی، volumeها و network داخلی در همان compose تعریف شده‌اند. `deploy` scripts برای `init/update/backup/restore/SSL` در `deploy/` قرار دارند.

## 18-7- اختیاری و Legacy بودن قابلیت‌ها

معماری پروژه بین قابلیت‌های فعال، اختیاری و `legacy` تمایز دارد:

| مورد | نوع | دلیل ثبت در معماری |
| --- | --- | --- |
| Stripe | اختیاری | `provider` و `webhook` وجود دارد، اما production پیش‌فرض زرین‌پال است. |
| WhiteNoise | اختیاری | fallback `static` است، نه مسیر اصلی production. |
| COD | Legacy | actionها و وضعیت‌ها برای سازگاری با داده/جریان قدیمی حفظ شده‌اند. |
| `courier/express` `delivery` | Legacy | مدل و status وجود دارد، اما `checkout` عمومی فعلی `pickup` است. |
| `counter_card` | `backend` compatibility | `provider` و method وجود دارد؛ گزینه عمومی `checkout` نیست. |

# 19- Architecture Summary

معماری Crumbs بر پایه appهای مستقل Django، service layer برای قوانین کسب‌وکار، تراکنش‌های صریح برای موجودی و پرداخت، PostgreSQL برای داده پایدار، Redis برای `cache/broker`، Celery برای کارهای پس‌زمینه، و Docker/Nginx/Gunicorn برای استقرار production ساخته شده است.

دلایل maintainability در وضعیت فعلی کد:

| عامل | توضیح |
| --- | --- |
| مرزبندی appها | هر دامنه اصلی مثل `orders`، `payments`، `inventory`، `growth` و `intelligence` محدوده مشخص دارد. |
| سرویس‌های دامنه | منطق حساس در serviceها قرار دارد و از پراکندگی در viewها جلوگیری شده است. |
| state machine سفارش | transitionها در یک جدول مجاز مرکزی کنترل می‌شوند. |
| تراکنش و lock | مسیرهای `checkout`، payment و stock با transaction و `select_for_update` محافظت شده‌اند. |
| `task`های پس‌زمینه | پردازش‌های دوره‌ای و غیرهمزمان از request lifecycle جدا شده‌اند. |
| settings محیطی | development، test و production از هم جدا هستند و secretها از environment خوانده می‌شوند. |
| Observability | health/readiness endpoints، structured `logs`، `BackgroundTaskLog` و Sentry اختیاری وجود دارند. |
| تست‌ها | unit، integration، edge case، Celery، production settings، migration history، SEO، `admin` و UI regression پوشش داده شده‌اند. |

دلایل آمادگی production از منظر معماری:

| حوزه | وضعیت |
| --- | --- |
| اجرای production | Dockerfile، Gunicorn و Docker Compose production موجود است. |
| reverse proxy | Nginx `config` و templateهای SSL وجود دارد. |
| پایگاه‌داده و `cache` | PostgreSQL و Redis در compose production تعریف شده‌اند. |
| background `processing` | Celery worker و beat با queueهای مشخص تعریف شده‌اند. |
| security settings | `DEBUG=False`، `ALLOWED_HOSTS`، `HTTPS/cookie/HSTS` و CSRF policy در settings کنترل می‌شوند. |
| health/readiness endpoints | health/readiness endpoints `/health/`، `/ready/` و `/health/full/` وجود دارند. |
| backup/restore | اسکریپت‌های `backup.sh` و `restore.sh` وجود دارند. |
| تست | نتیجه فعلی `421 passed, 4 skipped` است. |

برای تیم توسعه‌دهنده بعدی، نقاط ورود اصلی چنین هستند:

| نیاز | نقطه شروع |
| --- | --- |

| تغییر lifecycle سفارش | `delivery.state_machine` و `OrderService` |
| تغییر پرداخت | `payments.services` و `provider`های `payments/providers/` |

| تغییر عملیات کافه | `core.kitchen_views`، `core.pickup_views` و `admin` dashboards |
